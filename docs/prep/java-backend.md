# Java 后端与基建篇

> [!NOTE]
> 这一篇不是普通 Java 八股清单，而是用来证明你具备**后端基建能力、线上稳定性意识和复杂系统落地经验**。回答时始终围绕三层展开：底层原理、工程实践、线上风险兜底。

## 0. 回答总原则

面试官问 Java 后端问题时，真正想确认的不是你能否背出定义，而是你能不能把技术放进真实系统里。

- **先讲取舍**：不要直接说“用某个组件”，先说明为什么这个场景适合它。
- **再讲风险**：任何方案都有边界，比如线程池会打满、Redis 锁不是强一致、MQ 会重复消费。
- **最后讲兜底**：限流、降级、幂等、监控、告警、补偿、复盘，都是高级后端回答里的关键词。

> **一句话定位**：我不是只会写业务 CRUD，而是能把 Java 服务放在线上高并发、强依赖、可观测、可恢复的环境里稳定运行。

## 1. 并发编程与线程池治理

### 1.1 JUC 基础：锁、CAS、AQS

#### 核心知识

并发问题本质上围绕三件事：**原子性、可见性、有序性**。

- **原子性**：一个操作要么完整执行，要么不执行。`i++` 看起来是一行代码，底层通常包含读、加、写三个步骤，不是原子操作。
- **可见性**：一个线程修改共享变量后，其他线程能及时看到。CPU 缓存、编译器优化、线程工作内存都可能导致“读到旧值”。
- **有序性**：编译器和 CPU 可能在不改变单线程语义的前提下重排序，多线程下如果没有同步约束，就可能出现意料之外的执行顺序。

Java 通过 **JMM（Java Memory Model）** 定义线程之间如何通信。面试时可以用一句话概括：JMM 不是 JVM 内存结构，而是 Java 多线程下共享变量读写、内存屏障、happens-before 关系的一套规范。

常见 happens-before 规则：

- 程序次序规则：同一线程内，前面的操作 happens-before 后面的操作。
- 锁规则：对同一把锁，解锁 happens-before 后续加锁。
- volatile 规则：对 volatile 变量的写 happens-before 后续对它的读。
- 线程启动规则：`Thread.start()` happens-before 子线程内的操作。
- 线程终止规则：线程内所有操作 happens-before 其他线程检测到它结束，如 `join()` 返回。

**`synchronized`**：

- JVM 原生锁，进入同步块时加锁，退出同步块时自动释放锁，异常退出也会释放。
- 既保证互斥，也保证可见性：释放锁前会把工作内存中的共享变量刷新回主内存，获取锁后会重新读取主内存中的值。
- JDK 1.6 之后做了大量优化，如偏向锁、轻量级锁、自旋、锁粗化、锁消除，所以低冲突、小临界区场景性能并不差。
- 锁对象很重要：实例方法锁的是 `this`，静态方法锁的是 `Class` 对象，代码块锁的是括号里的对象。

**`ReentrantLock`**：

- JUC 显式锁，底层基于 AQS，功能比 `synchronized` 更灵活。
- 支持可中断获取锁：`lockInterruptibly()`，适合任务取消或超时控制。
- 支持尝试获取锁：`tryLock()` / `tryLock(timeout)`，获取不到可以降级、跳过或返回繁忙提示。
- 支持公平锁和非公平锁。公平锁按排队顺序获取，减少饥饿；非公平锁吞吐更高，是默认选择。
- 支持多个 `Condition` 条件队列，适合生产者消费者这种“不同条件分组等待”的场景。
- 必须在 `finally` 中释放锁，否则异常路径可能造成死锁。

**`volatile`**：

- 保证变量修改对其他线程可见，并通过内存屏障禁止特定指令重排。
- 不保证复合操作原子性。`volatile int count; count++` 仍然可能丢失更新。
- 适合状态标记、开关配置、单写多读场景，比如 `volatile boolean running` 控制线程退出。
- 不适合依赖“读-改-写”的计数场景，这类场景要用锁、`AtomicInteger`、`LongAdder`。

**CAS 与 Atomic 类**：

- CAS 是 Compare And Swap，核心是“当前值等于预期值才更新”，属于乐观并发控制。
- `AtomicInteger`、`AtomicLong`、`AtomicReference` 等类大量使用 CAS。
- 优点是低冲突下不用阻塞线程，吞吐好；缺点是高冲突下会反复自旋，浪费 CPU。
- CAS 还有 ABA 问题：值从 A 变成 B 又变回 A，CAS 会误以为没变过。可用版本号或 `AtomicStampedReference` 解决。
- 热点计数场景优先考虑 `LongAdder`，它通过分段计数降低单点 CAS 竞争，适合统计 QPS、埋点次数这类高并发累加。

**AQS（AbstractQueuedSynchronizer）**：

- AQS 是很多 JUC 同步器的底层骨架，比如 `ReentrantLock`、`Semaphore`、`CountDownLatch`、`ReentrantReadWriteLock`。
- 核心由两部分组成：一个 `volatile int state` 表示同步状态，一个 FIFO 等待队列保存获取资源失败的线程。
- 独占模式：同一时刻只有一个线程拿到资源，典型是 `ReentrantLock`。
- 共享模式：多个线程可以同时拿到资源，典型是 `Semaphore`、`CountDownLatch`。
- 获取锁失败的线程会被包装成 Node 进入等待队列，随后通过 `LockSupport.park()` 挂起，被前驱节点唤醒后再竞争。

**常用并发工具类**：

- `CountDownLatch`：一个或多个线程等待多个任务完成，计数不能重置，适合启动等待、批量任务汇总。
- `CyclicBarrier`：多个线程互相等待到达屏障后再一起继续，屏障可复用，适合分阶段并行任务。
- `Semaphore`：信号量，控制并发访问资源的数量，常用于限并发，如最多同时调用 20 个外部接口。
- `ConcurrentHashMap`：高并发 Map。JDK 8 使用 CAS + synchronized 锁桶头节点，读多写少场景性能很好。
- `CopyOnWriteArrayList`：写时复制，读无锁，适合读多写极少的监听器、配置快照，不适合频繁写入。

#### 线上风险

- 锁粒度过大，把远程调用、数据库查询放进锁里，导致吞吐下降。
- 高冲突 CAS 自旋，CPU 被空转消耗。
- `ThreadLocal` 使用后不清理，在线程池场景下可能造成上下文串号或内存泄漏。

#### 工程实践

- 简单临界区优先使用 `synchronized`，语义清楚、自动释放。
- 需要超时、可中断、多条件队列时使用 `ReentrantLock`。
- 锁内只做内存状态切换，不做慢 I/O。
- 使用 `try-finally` 清理锁和 `ThreadLocal`。

#### 面试 Q&A

**🧑‍💼 面试官**：你们项目里什么时候用 `ReentrantLock`，什么时候用 `synchronized`？

**🙋 您的话术**：
> “我不会机械地认为 `ReentrantLock` 一定比 `synchronized` 高级，而是看业务诉求。
> 
> 如果只是保护一小段临界区，比如本地缓存刷新时防止并发重建，我会优先用 `synchronized`，因为语义清晰、自动释放锁，出错概率低。现在 JVM 对它的优化已经很成熟，低冲突场景完全够用。
> 
> 如果需要更强的控制能力，比如获取锁超时后降级、任务取消时响应中断、或者一个锁下面有多个等待条件，我会选择 `ReentrantLock`。比如异步任务队列里，生产者要等队列有空位，消费者要等队列有数据，这种用 `Condition` 拆分等待队列更清楚。
> 
> 另外我会控制锁粒度，尽量只锁内存状态，不把远程调用和数据库查询放进锁里，否则锁本身没问题，系统吞吐也会被慢 I/O 拖垮。”

### 1.2 线程池参数设计与过载保护

#### 核心知识

`ThreadPoolExecutor` 的任务流转逻辑：

1. 当前线程数小于 `corePoolSize`，创建核心线程执行任务。
2. 达到 `corePoolSize` 后，任务进入 `workQueue`。
3. 队列满且线程数小于 `maximumPoolSize`，创建非核心线程。
4. 线程和队列都达到上限，触发拒绝策略。

线程池参数不能脱离业务类型。面试里不要只背 `corePoolSize`、`maximumPoolSize`，更重要的是讲清楚：**线程池不是为了无限接请求，而是为了把并发资源控制在系统可承受范围内**。

核心参数：

- **`corePoolSize`**：核心线程数，常驻处理任务。核心线程太小会导致队列快速堆积，太大则增加上下文切换和资源占用。
- **`maximumPoolSize`**：最大线程数，只在队列满后继续扩线程。使用无界队列时，这个参数基本不会生效。
- **`keepAliveTime`**：非核心线程空闲后的回收时间。突发流量场景可以适当保留一段时间，避免频繁创建销毁线程。
- **`workQueue`**：任务队列，是线程池削峰和排队的关键。生产环境要有界，避免把压力无限堆进内存。
- **`threadFactory`**：自定义线程名、优先级、异常处理，便于日志和监控定位。
- **`RejectedExecutionHandler`**：拒绝策略，是过载时的最后一道保护，不应该只用默认策略糊过去。

参数估算思路：

- **CPU 密集型**：线程数接近 CPU 核数，避免上下文切换过多。
- **I/O 密集型**：结合接口 RT、目标 QPS、下游承载能力估算，可用 `线程数 ≈ 目标 QPS × 平均 RT` 做初始值，再通过压测校准。例如目标 500 QPS，平均耗时 100ms，理论并发约 50，再结合 P95/P99、下游限额和机器 CPU 调整。
- **混合型任务**：不能只看平均 RT，要拆分 CPU 时间和等待时间。等待外部接口越多，线程数可以比 CPU 核数大；本地计算越重，线程数越要收敛。
- **队列必须有界**：无界队列会把压力堆进内存，最终 OOM 或长时间排队。
- **拒绝策略要业务化**：核心链路快速失败或降级，非核心任务进入 MQ 或补偿流程。

常见队列选择：

- **`ArrayBlockingQueue`**：有界数组队列，容量固定，适合容量明确、希望强约束排队长度的业务线程池。
- **`LinkedBlockingQueue`**：链表队列，可以有界也可以无界。生产环境不要使用默认无界容量。
- **`SynchronousQueue`**：不存储任务，提交任务必须直接交给工作线程，适合快速扩线程的场景，如 `newCachedThreadPool`，但要严格限制最大线程数。
- **`PriorityBlockingQueue`**：优先级队列，默认无界，使用时要特别注意容量和任务比较逻辑，否则容易内存膨胀或低优先级任务饥饿。

拒绝策略理解：

- **`AbortPolicy`**：直接抛异常，适合调用方能感知失败并快速返回的核心接口。
- **`CallerRunsPolicy`**：由提交任务的线程执行任务，可以形成背压，但如果提交线程是 Tomcat 请求线程、Kafka Poll Thread 或调度线程，可能把入口线程拖慢甚至拖死。
- **`DiscardPolicy`**：直接丢弃且不报错，风险高，只适合明确允许丢弃的统计类任务。
- **`DiscardOldestPolicy`**：丢弃队列最老任务再提交新任务，容易破坏任务时序，订单、状态流转类任务不能用。

线程池要和入口容器一起看：Tomcat 负责接收 HTTP 请求，业务线程池负责隔离具体业务任务。如果 Tomcat `maxThreads` 很大、业务线程池和队列也很大，突发流量会在多层同时堆积，故障恢复时间会被拉长。因此入口限流、Tomcat 连接数、业务线程池、数据库连接池、Redis 连接池要一起做容量匹配。

#### 线上风险

- 简单调大线程数，导致 CPU 上下文切换、内存占用、下游压力一起升高。
- 队列太大，请求长时间堆积，用户等很久后仍失败。
- 所有业务共用一个线程池，非核心任务拖垮核心链路。
- `CallerRunsPolicy` 无脑用于入口请求，可能把 Tomcat 线程拖死。

#### 工程实践

- 按业务拆线程池：核心交易、普通查询、通知、异步任务、大模型推理分别隔离。
- 监控活跃线程数、队列长度、拒绝次数、任务耗时。
- 入口先限流，线程池负责资源隔离和削峰，不负责无限接流量。
- Tomcat 的 `maxThreads`、`acceptCount`、`maxConnections` 也要一起控制。

#### 面试 Q&A

**🧑‍💼 面试官**：线上如果有突发高流量打过来，你们的线程池怎么配置以防止系统被压垮？

**🙋 您的话术**：
> “我们不会简单把线程池调大来扛突发流量，因为线程数越大，CPU 上下文切换、内存占用和下游压力都会上来，最后可能不是保护系统，而是把系统拖死。
> 
> 我们的思路是把线程池放在整个过载保护体系里看：入口限流、资源隔离、有界队列、拒绝策略、降级兜底、监控告警一起做。
> 
> 第一层是在网关或 Sentinel 做 QPS、并发线程数、热点参数限流，避免所有流量都打进业务线程池。第二层是按业务类型拆线程池，比如核心交易、查询、通知、异步任务不会共用一个池，避免低优先级任务占满核心资源。
> 
> 第三层是队列有界，队列不会设置特别大。队列太大会造成请求堆积，用户等很久之后还是失败，还会放大故障恢复时间。
> 
> 第四层是拒绝和降级。核心链路更倾向于快速失败或返回兜底数据，非核心异步任务可以进入 MQ 延迟处理或补偿。`CallerRunsPolicy` 我们会谨慎用，它适合某些内部异步任务做背压，但不适合无脑让 Tomcat 请求线程去执行长耗时任务。
> 
> 最后我们会监控线程池活跃线程数、队列长度、拒绝次数、任务耗时。一旦队列持续上涨或拒绝异常，就触发告警，联动调低限流阈值、打开降级开关，必要时扩容。”

### 1.3 ThreadLocal 与上下文泄漏风险

#### 核心知识

`ThreadLocal` 常用于保存用户上下文、TraceId、租户信息、数据源路由标记。它解决的是“同一个线程内跨方法传递上下文”的问题，不是线程间共享数据的工具。

底层可以这样理解：每个线程对象里都有一个 `ThreadLocalMap`，`ThreadLocal` 本身作为 key，业务放进去的对象作为 value。调用 `threadLocal.set(value)` 时，实际是把 value 放到了当前线程自己的 Map 里。

几个关键点：

- `ThreadLocal` 的值绑定在线程上，而不是请求上。
- Web 容器和业务线程池都会复用线程，请求结束后线程不会销毁。
- 如果不执行 `remove()`，旧 value 可能一直挂在线程上，造成内存泄漏或上下文串号。
- `ThreadLocalMap` 里的 key 是弱引用，但 value 是强引用。key 被 GC 后，value 不会自动立刻释放，只有后续访问 Map 触发清理逻辑时才可能被清掉。
- `InheritableThreadLocal` 只能在线程创建时把父线程值复制给子线程，在线程池复用场景并不能天然解决异步上下文传递。

典型使用场景：

- 登录用户上下文：Controller、Service、DAO 层都需要拿当前用户信息。
- TraceId：日志链路追踪，避免每个方法都传 `traceId` 参数。
- 租户 ID：多租户系统做数据隔离或数据源路由。
- 灰度标记：把当前请求命中的灰度策略传到下游调用。

典型风险：

- 用户上下文串号：A 用户请求结束未清理，B 用户复用同一线程后读到 A 的用户信息。
- TraceId 串号：日志被串到其他请求下，排障时误判调用链。
- 大对象泄漏：把 request、response、大集合放进 ThreadLocal，线程长期不销毁，内存持续被占用。
- 异步丢上下文：主线程有用户信息，提交到线程池后子线程拿不到，导致审计日志、租户路由、权限判断异常。

#### 工程实践

- 在过滤器或拦截器中设置上下文，并在 `finally` 中统一 `remove()`。
- ThreadLocal 里只放轻量上下文 ID，不放 `HttpServletRequest`、大集合、大对象。
- 异步任务中要显式传递上下文，不能默认认为子线程能拿到父线程上下文。
- 对公共线程池可以封装 `TaskDecorator` 或包装 `Runnable` / `Callable`，提交任务时复制必要上下文，任务结束后清理。
- 链路追踪优先用成熟组件的上下文传播机制，如 SkyWalking、OpenTelemetry、TransmittableThreadLocal，而不是每个业务手写一套。

#### 面试 Q&A

**🧑‍💼 面试官**：`ThreadLocal` 在线上有什么坑？

**🙋 您的话术**：
> “最大的问题是线程池复用。`ThreadLocal` 的生命周期跟线程绑定，而 Web 请求结束后线程不会销毁，会回到线程池。如果没有 `remove()`，下一个请求复用这个线程时可能读到上一个用户的上下文，轻则日志 TraceId 串号，重则权限和租户数据串号。
> 
> 所以我们一般在过滤器里设置用户上下文和 TraceId，在 `finally` 里清理。异步任务也不会默认依赖 `ThreadLocal`，而是显式传递必要上下文。”

## 2. JVM 与线上排障主线

### 2.1 JVM 内存结构与对象生命周期

#### 核心知识

JVM 这一块不要只背“堆、栈、方法区”，更重要的是能把内存区域和线上现象关联起来：堆高对应对象存活，栈高对应线程和调用深度，元空间高对应类加载，直接内存高对应 NIO/Netty/堆外缓存。

**运行时内存区域**：

- **堆（Heap）**：对象主要分配区域，也是 GC 最核心的管理区域。常见问题是 `Java heap space`、老年代持续上涨、Full GC 后降不下来。
- **虚拟机栈（Java Virtual Machine Stack）**：线程私有，每次方法调用会创建栈帧，里面包含局部变量表、操作数栈、动态链接、返回地址。递归过深或栈帧过大可能导致 `StackOverflowError`。
- **本地方法栈**：给 Native 方法使用，业务开发直接接触较少，但底层库、JNI、加密压缩库可能涉及。
- **程序计数器**：线程私有，记录当前线程执行到哪条字节码指令。它很小，基本不会成为线上内存瓶颈。
- **方法区 / 元空间（Metaspace）**：存放类元信息、方法元信息、常量池相关信息。JDK 8 后永久代被元空间替代，元空间默认使用本地内存。动态代理、频繁热部署、类加载器泄漏可能导致 Metaspace 增长。
- **直接内存（Direct Memory）**：不属于 JVM 堆，但属于进程内存。NIO、Netty、RocketMQ、Kafka Client 等都可能使用。典型现象是堆监控不高，但进程 RSS 很高，甚至触发容器 OOM Kill。

**对象分配与生命周期**：

- 大多数对象优先在 Eden 区分配。
- Eden 满了触发 Young GC，存活对象进入 Survivor 区。
- 对象在 Survivor 区经历多次 GC 后达到年龄阈值，晋升到老年代。
- 大对象可能直接进入老年代，避免在年轻代反复复制。
- 如果 Survivor 空间不足，部分对象会提前晋升老年代，这会增加 Full GC 风险。

**判断对象是否可回收**：

- JVM 主流使用可达性分析，而不是简单引用计数。
- 从 GC Roots 出发，能被引用链到达的对象是存活对象，不能到达的对象才可能被回收。
- 常见 GC Roots 包括线程栈中的局部变量、静态变量、常量引用、JNI 引用、被 synchronized 持有的对象。

**四种引用类型**：

- **强引用**：最常见，只要强引用存在，对象不会被 GC。
- **软引用**：内存不足时才回收，适合缓存，但现在更推荐用 Caffeine 这类可控缓存。
- **弱引用**：下一次 GC 就可能回收，`ThreadLocalMap` 的 key 就是弱引用。
- **虚引用**：主要用于跟踪对象回收过程，如堆外内存释放。

**类加载机制**：

- 类加载过程包括加载、验证、准备、解析、初始化。
- 双亲委派模型让类加载优先交给父加载器，避免核心类被应用自定义类篡改。
- 常见破坏双亲委派的场景有 SPI、Tomcat 多应用隔离、OSGi、部分插件化框架。
- 线上如果 Metaspace 持续增长，要重点看动态生成类、类加载器是否可回收、是否存在反复创建 ClassLoader 的逻辑。

### 2.2 GC 选型与调优思路

#### 核心知识

JVM 调优目标不是“GC 次数最少”，而是让业务在可接受的吞吐、延迟和资源成本下稳定运行。一次调优前要先明确目标：是降低接口 P99、减少 Full GC、提升吞吐，还是解决内存泄漏。

**常见 GC 概念**：

- **Minor GC / Young GC**：回收年轻代，通常频率高、停顿短。
- **Major GC / Old GC**：回收老年代，不同收集器定义略有差异，面试中说明即可。
- **Full GC**：通常会涉及整个堆和元空间，停顿更明显，线上需要重点关注。
- **STW（Stop The World）**：GC 时暂停业务线程。低延迟服务关注的不是平均 GC，而是 STW 对 P95/P99 的影响。

**常见收集器选择**：

- **Serial GC**：单线程收集，适合小内存、客户端或测试环境，服务端很少主动选。
- **Parallel GC**：关注吞吐，适合后台批处理、离线任务，对低延迟要求不高。
- **CMS**：老版本低停顿收集器，已逐步被 G1 替代。它有并发模式失败、内存碎片等问题。
- **G1**：面向服务端的通用选择，把堆切成 Region，兼顾吞吐和停顿控制。适合大多数中大堆在线服务。
- **ZGC / Shenandoah**：面向超低停顿和大堆场景，停顿时间可以做到毫秒级，但要结合 JDK 版本、运维工具链和团队经验评估。

**G1 重点理解**：

- G1 不再固定按物理连续的新生代、老年代划分，而是把堆拆成多个 Region。
- 它会优先回收收益高的 Region，因此叫 Garbage First。
- `-XX:MaxGCPauseMillis` 是期望停顿目标，不是硬保证。目标设得过低，可能导致 GC 更频繁，反而影响吞吐。
- Humongous Object（大对象）会占用连续 Region，大量大对象容易导致空间碎片和 Full GC。

**基础参数原则**：

- 生产环境通常设置 `-Xms` 和 `-Xmx` 相等，减少运行期堆扩缩容抖动。
- 容器环境要关注 JVM 是否正确识别 cgroup 限制，避免堆设置过大挤压直接内存、线程栈和 Metaspace。
- 不要只看堆大小，还要预留直接内存、线程栈、Metaspace、Code Cache、Native 库内存。
- GC 日志必须打开，并接入日志采集，线上问题发生后没有 GC 日志会非常被动。

**调优基本顺序**：

1. 先看业务现象：RT 抖动、CPU 高、内存涨、容器重启、接口超时。
2. 再看监控：堆、非堆、GC 次数和耗时、线程数、CPU、RSS、接口 P99。
3. 分析 GC 日志：Young GC 是否过频、Full GC 是否频繁、老年代回收后是否下降。
4. 定位对象来源：HeapDump、MAT、对象直方图、GC Roots。
5. 最后调参数：堆大小、年轻代比例、收集器、停顿目标、直接内存限制。

#### 线上风险

- Full GC 频繁导致 STW，接口 RT 抖动甚至超时。
- 老年代持续上涨，Full GC 后降不下来，可能有内存泄漏。
- 直接内存泄漏时，堆监控不高，但进程 RSS 持续上涨。

#### 面试 Q&A

**🧑‍💼 面试官**：如果一个 Java 服务频繁 Full GC，你会怎么排查？

**🙋 您的话术**：
> “我会先区分这是内存泄漏、内存配置不合理，还是业务瞬时大对象导致的压力。
> 
> 第一阶段先看监控和 GC 日志：Full GC 的频率、每次停顿时间、老年代回收前后是否明显下降。如果 Full GC 后老年代占用仍然很高，说明大概率有长期存活对象。
> 
> 第二阶段保留现场，用 `jstat` 看各代使用率，用 `jmap` 或自动 HeapDump 拿内存快照，再用 MAT 分析 `Dominator Tree` 和 GC Roots，定位到底是哪个集合、缓存、线程上下文或者静态变量持有了大量对象。
> 
> 第三阶段看业务模式。如果是报表导出、批量查询、文件解析，我会优先检查是否一次性加载了大量数据，改成分页、游标或流式处理。如果是缓存导致，就要加容量上限、过期策略和监控。
> 
> 最后才是调 JVM 参数。我的原则是先找对象来源和业务根因，再做参数优化，否则只是把故障推迟发生。”

### 2.3 OOM / CPU 飙高 / Arthas 主线

#### 核心知识

- OOM 先保留现场：异常日志、GC 日志、监控时间点、HeapDump、线程栈。生产建议配置 `-XX:+HeapDumpOnOutOfMemoryError` 和 `-XX:HeapDumpPath`。
- OOM 类型要先区分：`Java heap space` 是堆不够或对象泄漏；`Metaspace` 多和类加载有关；`unable to create new native thread` 多和线程数过多或系统限制有关；`Direct buffer memory` 多和堆外内存有关。
- CPU 高先区分业务线程高还是 GC 线程高。业务线程高看热点栈，GC 线程高看是否频繁 GC 或内存分配过快。
- 线程问题要看状态：`RUNNABLE` 不一定是正常运行，也可能卡在本地方法；`BLOCKED` 多是锁竞争；`WAITING/TIMED_WAITING` 要看是在等锁、等队列、等网络还是等定时任务。
- Arthas 常用命令：`dashboard` 看整体状态，`thread -n 3` 查高 CPU 线程，`thread -b` 查死锁，`trace` 看调用链耗时，`watch` 看方法入参返回异常，`jad` 反编译线上类。
- MAT 常用视角：`Leak Suspects` 快速看疑似泄漏，`Dominator Tree` 看谁支配了大量对象，`Path to GC Roots` 看对象为什么没被回收，Histogram 看对象数量和类型分布。

**常见 OOM 根因**：

- 一次性加载大数据：报表导出、批量查询、文件解析把所有数据放进 List。
- 缓存没有上限：本地 Map、Guava/Caffeine 配置不当，或者只写不淘汰。
- ThreadLocal 未清理：线程池复用导致上下文对象长期挂在线程上。
- 异步队列堆积：生产速度大于消费速度，队列里堆满任务和业务对象。
- 动态类过多：频繁生成代理类、脚本类、表达式类，类加载器无法回收。
- 堆外内存泄漏：Netty ByteBuf 未释放，NIO DirectBuffer 过多。

**CPU 飙高排查路径**：

1. `top` 找到高 CPU Java 进程。
2. `top -Hp <pid>` 找到高 CPU 线程 ID。
3. 把线程 ID 转成 16 进制，对应 `jstack` 里的 `nid`。
4. 看线程栈是在业务循环、正则匹配、JSON 序列化、锁竞争，还是 GC 线程。
5. 用 Arthas `thread -n 3` 可以把这几步压缩成一次命令。

**慢接口排查路径**：

- 先看链路追踪，判断耗时在入口、业务代码、DB、Redis、MQ 还是外部 HTTP。
- 再用 Arthas `trace` 定位具体方法耗时。
- 如果单方法入参异常，用 `watch` 观察参数、返回值和异常。
- 如果怀疑代码版本不一致，用 `jad` 看线上实际字节码反编译结果。

> [!TIP]
> 本节只保留 JVM 面试主线。更完整的线上故障 SOP，包括 CPU 飙高、线程池打满、数据库连接池耗尽、慢接口、死锁和 GC 日志判断，见 [JVM 与线上问题排查专项](/prep/jvm-troubleshooting)。

#### 面试 Q&A

**🧑‍💼 面试官**：能分享一次 OOM 或 CPU 飙高的排查经历吗？

**🙋 您的话术**：
> “有一次批量数据导出服务在周一高峰频繁假死，监控显示内存持续上涨，Full GC 很频繁，接口 RT 也明显抖动。
> 
> 因为生产 JVM 提前配置了 HeapDump，我拿到 Dump 后用 MAT 看 `Leak Suspects` 和 `Dominator Tree`，发现一个 `ArrayList` 占用了大量堆内存。沿着 `Path to GC Roots` 追下去，定位到导出逻辑一次性把几十万条记录加载进内存。
> 
> 修复上，我们把 MyBatis 查询改成游标或分批读取，边读边写文件，不再一次性持有所有数据。同时用 Arthas `thread -n 3` 确认 CPU 高主要来自频繁 GC。上线后内存稳定在正常水位，这类大批量查询也进入了 Code Review 检查项。”

## 3. MySQL 索引、事务与慢 SQL

### 3.1 B+ 树、聚簇索引与回表

#### 核心知识

MySQL 索引不要只背“B+ 树”，要能说清楚它为什么适合数据库：**树高低、磁盘 I/O 少、范围查询友好、排序能力强**。

**为什么 InnoDB 用 B+ 树**：

- B+ 树是多路平衡搜索树，一个节点能存很多 key，树高通常很低，千万级数据也可能只有 3 到 4 层。
- 非叶子节点只存索引 key 和指针，不存完整行，因此单页能容纳更多 key，减少磁盘 I/O。
- 叶子节点之间通过链表连接，天然支持范围查询和顺序扫描。
- 相比哈希索引，B+ 树不仅能等值查询，还能范围查询、排序、前缀匹配。
- 相比红黑树，B+ 树更适合磁盘页读取，因为红黑树树高更高，随机 I/O 更多。

**聚簇索引与二级索引**：

- InnoDB 主键索引是**聚簇索引**，叶子节点存完整行数据。
- 一张表只能有一个聚簇索引，因为数据行本身只能按一种方式组织。
- 普通索引也叫二级索引或非聚簇索引，叶子节点存的是主键值。
- 通过普通索引查完整行时，需要先在普通索引中找到主键，再回到主键索引查整行，这就是回表。
- 覆盖索引是指查询所需字段都在同一个索引里，直接从索引返回，不需要回表。

**主键设计影响**：

- 推荐使用递增或趋势递增主键，比如自增 ID、雪花 ID。随机 UUID 会导致页分裂、索引碎片和写入放大。
- 主键不宜过长，因为二级索引叶子节点会存主键值，主键越大，所有二级索引体积都会变大。
- 业务唯一字段可以建唯一索引，但不一定适合作为主键，尤其是很长、会变化或无序的字段。

**回表与索引下推**：

- 回表不是一定有问题，关键看回表次数。如果筛选后只回表几十行，影响很小；如果回表几十万行，就会很慢。
- 覆盖索引可以减少回表，适合高频列表页和只查少量字段的查询。
- 索引下推（Index Condition Pushdown）可以在存储引擎层先用索引中的字段做过滤，减少回表次数。

### 3.2 联合索引、覆盖索引与索引失效

#### 核心知识

联合索引设计的核心不是“字段越多越好”，而是让查询条件、排序、分组和返回字段尽量在同一棵索引树上完成。

**最左前缀原则**：

- 联合索引 `(a, b, c)` 可以支持 `a`、`a,b`、`a,b,c` 这类从左到右连续匹配。
- 如果跳过最左列，比如只查 `b` 或 `b,c`，通常无法充分利用这个联合索引。
- 等值条件可以乱序书写，优化器会重排；但索引设计仍要按业务过滤能力和排序需求安排字段顺序。
- 范围查询后的字段通常无法继续用于有序定位。例如 `(a,b,c)` 中 `a = ? and b > ? and c = ?`，`c` 可能只能做过滤，不能继续缩小索引扫描范围。

**联合索引字段顺序**：

- 高频等值过滤字段靠前。
- 区分度高的字段通常靠前，但不能只看区分度，还要看是否高频、是否参与排序。
- 范围字段尽量放在等值字段之后。
- 排序字段要结合 `where` 条件设计，尽量避免额外 filesort。
- 如果查询只返回少量列，可以把返回列放进联合索引形成覆盖索引。

**常见索引失效场景**：

- 对索引列使用函数：`DATE_FORMAT(create_time)`、`LOWER(name)`。
- 对索引列做表达式计算：`age + 1 = 20`。
- 隐式类型转换：字符串字段用数字查询，如 `phone = 13800138000`。
- 前置模糊匹配：`like '%abc'` 通常无法走普通 B+ 树索引。
- `or` 两边字段索引设计不一致，可能导致优化器放弃索引。
- 低选择性字段单独建索引效果差，比如性别、状态位，要结合其他字段建联合索引。

**EXPLAIN 重点字段**：

- `type`：访问类型，从好到差大致是 `const`、`eq_ref`、`ref`、`range`、`index`、`ALL`。线上高频查询尽量避免 `ALL`。
- `key`：实际使用的索引，不是可能使用的索引。
- `rows`：预估扫描行数，越大风险越高。
- `filtered`：过滤后剩余比例，过低说明扫描了很多无效数据。
- `Extra`：重点关注 `Using index`、`Using where`、`Using filesort`、`Using temporary`。
- `Using index` 通常表示覆盖索引；`Using filesort` 表示需要额外排序；`Using temporary` 多见于复杂排序、分组、去重，需要重点优化。

#### 工程实践

- 查询条件、排序字段、返回字段一起考虑联合索引，而不是看到一个字段就建一个单列索引。
- 只查必要字段，避免 `select *`，让高频列表查询尽量走覆盖索引。
- 慢 SQL 优化先看执行计划和数据分布，不要凭感觉加索引。
- 索引不是越多越好，写入、更新、删除都要维护索引，过多索引会拖慢写入并增加磁盘占用。
- 对大表加索引要评估锁表、回滚、主从延迟和变更窗口，必要时使用在线 DDL 或变更工具。

#### 面试 Q&A

**🧑‍💼 面试官**：你们项目中遇到过慢 SQL 吗？怎么排查和优化？

**🙋 您的话术**：
> “在 OTT 设备管理系统里遇到过设备列表分页接口变慢。设备量上来后，接口从几十毫秒涨到 3 秒多。
> 
> 我先从慢查询日志拿到 SQL，再用 `EXPLAIN` 看执行计划，发现 `type` 是 `ALL`，`Extra` 里还有 `Using filesort`。继续看代码，发现查询日期时用了 `DATE_FORMAT(create_time, '%Y-%m-%d')`，对索引字段做函数操作，破坏了 B+ 树有序性，导致索引失效。
> 
> 修复时我把它改成范围查询：`create_time >= '2023-10-01 00:00:00' and create_time < '2023-10-02 00:00:00'`。同时根据查询条件和排序补了 `(device_type, create_time)` 联合索引。上线后走到了索引范围扫描，接口恢复到几十毫秒。”

### 3.3 MVCC、隔离级别与锁机制

#### 核心知识

事务的核心是 ACID，但面试里更重要的是能讲清楚隔离级别、MVCC 和锁如何影响线上并发。

**ACID**：

- **原子性**：事务内操作要么都成功，要么都失败，依赖 Undo Log 回滚。
- **一致性**：事务执行前后数据满足业务约束，比如余额不能为负、订单状态不能乱跳。
- **隔离性**：多个事务并发执行时互不干扰，由隔离级别、MVCC、锁共同保证。
- **持久性**：事务提交后数据不能丢，依赖 Redo Log 刷盘和崩溃恢复。

**隔离级别**：

- **读未提交（RU）**：可能读到未提交数据，基本不用。
- **读已提交（RC）**：只能读到已提交数据，解决脏读，但可能不可重复读。
- **可重复读（RR）**：InnoDB 默认级别，同一事务中多次快照读结果一致。
- **串行化（Serializable）**：隔离最强，并发最差，通常不用在高并发业务。

**MVCC 实现要点**：

- InnoDB 每行记录有隐藏字段，如 `DB_TRX_ID` 记录最近修改事务 ID，`DB_ROLL_PTR` 指向 Undo Log 版本链。
- Undo Log 不只用于回滚，也用于构建历史版本，支持快照读。
- ReadView 决定当前事务能看到哪些版本。
- RC 和 RR 的核心区别是 ReadView 生成时机：RC 每次快照读生成新的 ReadView，RR 通常在事务第一次快照读时生成 ReadView。

**快照读与当前读**：

- 普通 `select` 通常是快照读，通过 MVCC 读取历史版本，不加锁。
- `select ... for update`、`select ... lock in share mode`、`update`、`delete` 属于当前读，读最新版本，并可能加锁。
- RR 下快照读通过 MVCC 避免幻读；当前读通过 Next-Key Lock 避免幻读。

**InnoDB 锁类型**：

- **行锁（Record Lock）**：锁住具体索引记录。
- **间隙锁（Gap Lock）**：锁住索引记录之间的间隙，防止其他事务插入新记录。
- **临键锁（Next-Key Lock）**：行锁 + 间隙锁，锁住一个左开右闭区间。
- **意向锁**：表级锁，用于表示事务接下来要对表中某些行加共享锁或排他锁，方便表锁和行锁兼容判断。

**关键结论**：

- InnoDB 的行锁是加在索引上的，不是直接加在“行对象”上。
- SQL 不走索引时，可能扫描大量记录并扩大锁范围，高并发下容易阻塞。
- 唯一索引等值命中通常只加记录锁；范围查询更容易产生 Next-Key Lock。
- 事务里不要做远程调用和长时间计算，否则会长时间持有数据库锁和连接。

### 3.4 慢 SQL、死锁与深分页优化

#### 核心知识

慢 SQL、死锁、深分页是 MySQL 线上最常见的三类问题，排查时要先定位“慢在哪里”：扫描行数多、排序临时表、锁等待、连接池等待、还是磁盘/CPU 资源瓶颈。

**慢 SQL 常见原因**：

- 没有合适索引，导致全表扫描。
- 索引失效，导致扫描行数远大于返回行数。
- 返回字段太多或回表次数太多。
- 排序、分组、去重使用临时表或 filesort。
- 深分页 offset 太大，数据库需要扫描并丢弃大量数据。
- 锁等待，不是 SQL 本身慢，而是在等其他事务释放锁。

**深分页问题**：

- `limit 100000, 20` 并不是直接跳到第 100000 行，而是扫描前 100020 行，再丢弃前 100000 行。
- 如果还需要回表，深分页会造成大量无效回表。
- 常见优化是基于游标翻页：`where id > last_id order by id limit 20`。
- 如果必须支持任意页跳转，可以先用覆盖索引查出主键，再根据主键回表查询完整数据。

**死锁本质**：

- 两个或多个事务互相持有对方需要的锁，形成等待环。
- InnoDB 会检测死锁，并回滚其中一个事务。
- 死锁不是“数据库坏了”，而是并发访问顺序和锁范围设计有问题。

#### 工程实践

- 慢 SQL：慢日志定位 SQL，`EXPLAIN` / `EXPLAIN ANALYZE` 看执行计划，结合数据量和索引选择做优化。
- 死锁：看 `SHOW ENGINE INNODB STATUS` 的 latest detected deadlock，找到两个事务的 SQL、持锁和等待锁。
- 深分页：用 `where id > last_id limit n`，或者先走覆盖索引查主键，再回表查详情。
- 大事务：拆小事务，不在事务里做 RPC、HTTP、MQ 同步等待。
- 热点更新：通过分片、队列串行化、乐观锁版本号、状态机降低同一行并发竞争。
- 连接池：慢 SQL 会占用连接，连接池打满后会拖垮应用线程池，要把 DB 连接池指标纳入监控。

#### 面试 Q&A

**🧑‍💼 面试官**：线上 MySQL 死锁怎么定位和解决？

**🙋 您的话术**：
> “我会先明确，死锁不能只靠重试掩盖，重试只是兜底，根因还是加锁顺序和索引。
> 
> 排查时先看应用日志里的死锁 SQL，然后执行 `SHOW ENGINE INNODB STATUS`，看两个事务分别持有哪些锁、等待哪些锁。很多死锁来自两个事务更新资源顺序不一致，比如 A 先订单后库存，B 先库存后订单。
> 
> 解决上优先统一加锁顺序，检查 SQL 是否命中索引，避免锁范围扩大；再把大事务拆小，不在事务里做远程调用。工程上会对死锁异常做有限重试，但前提是业务幂等。”

## 4. Redis 缓存与分布式协调

### 4.1 缓存穿透、击穿、雪崩

#### 核心知识

Redis 在后端系统里主要承担三类角色：**缓存、分布式协调、计数/限流**。面试时不要只说“Redis 很快”，要说清楚它快在哪里，以及快的代价是什么。

**Redis 为什么快**：

- 数据主要在内存里，避免磁盘随机 I/O。
- 单线程执行命令，避免大量线程切换和锁竞争。这里的单线程主要指命令执行线程，Redis 6 之后网络 I/O 可以多线程。
- I/O 多路复用，用少量线程处理大量连接。
- 数据结构紧凑，针对不同编码做了优化，如 ziplist/listpack、intset、skiplist、hashtable。

**常用数据结构与场景**：

- **String**：缓存对象、计数器、分布式锁、验证码。
- **Hash**：对象字段缓存，适合部分字段更新，但大 Hash 要注意拆分。
- **List**：简单队列、时间线，但复杂消息场景更推荐 MQ。
- **Set**：去重、共同好友、标签集合。
- **ZSet**：排行榜、延迟队列、滑动窗口限流。
- **Bitmap**：签到、活跃标记、布尔状态统计。
- **HyperLogLog**：UV 估算，节省内存但有误差。

**缓存穿透、击穿、雪崩**：

- **缓存穿透**：查询不存在的数据，缓存和 DB 都没有，每次请求都打到 DB。防御方式是布隆过滤器、空值缓存、参数校验。
- **缓存击穿**：某个热点 Key 过期瞬间，大量并发请求同时打 DB。防御方式是互斥锁、逻辑过期、热点预热、单飞机制。
- **缓存雪崩**：大量 Key 同时过期，或 Redis 整体不可用，流量集中打 DB。防御方式是随机 TTL、多级缓存、限流降级、熔断和预热。

**过期与淘汰**：

- Redis 过期删除不是每个 Key 到期立刻删除，而是惰性删除 + 定期删除结合。
- 内存达到 `maxmemory` 后会触发淘汰策略，如 `allkeys-lru`、`volatile-lru`、`allkeys-lfu`、`noeviction`。
- 缓存型 Redis 通常会设置 `maxmemory` 和合适淘汰策略；如果是分布式锁、队列、关键状态，不应依赖随机淘汰。

**缓存设计原则**：

- 缓存只兜读性能，不应该成为唯一数据源。
- Key 要有命名规范，包含业务、环境、版本，避免冲突。
- Value 要控制大小，避免大 Key 造成网络阻塞、迁移变慢、删除卡顿。
- TTL 要有随机抖动，避免同一时间大量过期。
- 核心缓存要有命中率、RT、Key 数量、内存使用、慢命令监控。

### 4.2 多级缓存与热点 Key 治理

#### 核心知识

多级缓存的目标不是“多加一层缓存显得高级”，而是在 Redis 抖动、热点突增、网络延迟升高时，减少对 Redis 和 DB 的冲击。

**典型结构**：

- L1 本地缓存：Caffeine / Guava，部署在应用 JVM 内，访问最快，但多实例之间不天然一致。
- L2 分布式缓存：Redis，跨实例共享，适合大多数热点读。
- L3 数据库：最终权威数据源，不能被突发读流量直接打穿。

**热点 Key 风险**：

- 某个 Key 请求量远高于其他 Key，会让单个 Redis 节点、单个网络连接或单个应用实例压力过高。
- Redis Cluster 下同一个 Key 只能落到一个槽位对应的主节点，热 Key 不会自动分散到多个分片。
- 热 Key 如果恰好过期，会触发缓存击穿。

**大 Key 风险**：

- 单个 Key 的 value 很大，读写会占用大量网络带宽。
- 删除大 Key 可能阻塞 Redis 主线程，影响其他请求。
- 主从同步、AOF 重写、Cluster 迁移时，大 Key 会放大延迟和抖动。

**常见治理方式**：

- 热点预热：活动开始前把核心数据提前加载进 Redis 和本地缓存。
- 本地缓存：核心热点读先查 Caffeine，降低 Redis 压力。
- 热点拆分：把一个热点 Key 拆成多个副本 Key，读时随机访问。
- 逻辑过期：热点 Key 不直接过期，后台异步刷新，前台先返回旧值。
- 大 Key 拆分：把大 Hash、大 List、大 Set 按业务维度拆成多个小 Key。
- 异步删除：删除大 Key 用 `UNLINK`，避免 `DEL` 阻塞主线程。

#### 工程实践

- L1 本地缓存：Caffeine，抗热点、抗 Redis 短时抖动。
- L2 分布式缓存：Redis，跨实例共享。
- 热 Key：本地缓存、热点探测、Key 拆分、多副本读。
- 大 Key：拆分、压缩、限制集合长度、用 `UNLINK` 异步删除。

#### 面试 Q&A

**🧑‍💼 面试官**：Redis 集群不可用了，你们系统能扛住吗？

**🙋 您的话术**：
> “如果只依赖 Redis 单层缓存，Redis 不可用时流量会瞬间打到 MySQL，这是典型缓存雪崩。
> 
> 对核心高频读接口，我们会用 Caffeine + Redis 二级缓存。请求先查 JVM 内存里的 Caffeine，未命中再查 Redis，最后才查 DB。Redis 抖动时，Caffeine 至少能兜住大部分热点读流量。
> 
> 数据一致性上，我们会通过消息广播或 Binlog 监听驱逐本地缓存，并给本地缓存设置较短 TTL 和容量上限。这样既提升读性能，也能在 Redis 故障时给系统争取恢复时间。”

### 4.3 缓存一致性方案

#### 核心知识

缓存一致性不是追求“缓存和 DB 永远强一致”，而是根据业务容忍度控制脏数据窗口。多数互联网业务采用最终一致性，核心写链路用 DB 约束、事务、状态机兜底。

**Cache Aside 模式**：

- 读请求：先读缓存，未命中再读 DB，然后把结果写入缓存。
- 写请求：先更新 DB，再删除缓存。
- 删除缓存优于更新缓存，因为更新缓存在并发写下更容易把旧值写回缓存。

**为什么不是先删缓存再更新 DB**：

- 线程 A 先删除缓存，还没更新 DB。
- 线程 B 读缓存未命中，读取旧 DB 值并写回缓存。
- 线程 A 更新 DB 成功。
- 结果缓存里长期保存旧值，直到 TTL 过期。

**为什么更新 DB 后删除缓存仍可能不一致**：

- DB 更新成功，但删除缓存失败，会继续读到旧缓存。
- 删除缓存成功后，如果有并发读用旧 DB 结果回填，也可能短时间不一致。
- 主从延迟场景下，如果读从库再回填缓存，可能把旧值写入缓存。

**兜底手段**：

- 删除失败记录日志，投递重试任务。
- 监听 Binlog，把 DB 变更转换成缓存删除事件。
- 缓存设置 TTL，作为最终兜底。
- 对强一致读场景，写后短时间直接读主库或绕过缓存。
- 对核心状态变更，依赖 DB 乐观锁、唯一索引、状态机，不把缓存当一致性来源。

**延迟双删的边界**：

- 延迟双删是“更新 DB 前删一次，更新后延迟再删一次”的经验方案，可降低并发回填旧值概率。
- 它不能严格证明强一致，延迟时间也难以精确选择，生产上更推荐删除重试、Binlog 订阅和 TTL 兜底。

#### 面试 Q&A

**🧑‍💼 面试官**：更新数据库和删除缓存不是原子操作，中间失败怎么办？

**🙋 您的话术**：
> “这个问题本质是缓存和数据库一致性。我们一般采用 Cache Aside，写请求先更新数据库，再删除缓存。
> 
> 如果数据库成功但删除缓存失败，确实会短时间读到旧缓存。我们会做几层兜底：删除失败记录日志并投递重试任务；也可以监听 Binlog，把数据变更转换成缓存删除事件；对一致性要求没那么高的业务，缓存设置较短 TTL，让脏数据最多存在一个可控窗口。
> 
> 我们不太倾向更新缓存，因为并发写时容易出现后写 DB 的请求先更新缓存、先写 DB 的请求后更新缓存，导致缓存反而变旧。删除缓存让下一次读重新从 DB 加载，整体更稳。”

### 4.4 Redis 分布式锁与 Redisson

#### 核心知识

Redis 分布式锁适合高并发、低延迟、允许最终一致兜底的业务协调场景。它不适合作为金融级强一致的唯一保障。

**正确加锁方式**：

- 加锁用 `SET lock_key unique_value NX PX timeout`。
- `NX` 保证只有 Key 不存在时才能设置成功。
- `PX timeout` 保证锁有过期时间，避免持锁线程崩溃后永远不释放。
- `unique_value` 要能标识当前请求或线程，通常用 UUID、线程 ID、请求 ID 组合。

**正确释放方式**：

- 释放锁前必须判断 value 是不是自己。
- 判断和删除必须用 Lua 脚本保证原子性。
- 不能简单 `DEL lock_key`，否则业务执行超时导致锁过期后，其他线程拿到新锁，旧线程再执行 DEL 会误删别人的锁。

**Redisson 做了什么**：

- 支持可重入锁，同一个线程重复加锁会计数。
- 使用 Lua 脚本保证释放锁的原子性。
- Watchdog 自动续期：没有显式指定 leaseTime 时，业务还在执行就会定期延长锁过期时间。
- 提供公平锁、读写锁、信号量等封装，但使用前要确认业务是否真的需要这些语义。

**锁粒度与锁时长**：

- 锁粒度尽量细，如 `orderId`、`userId`、`deviceId`，避免全局锁降低吞吐。
- 锁内只做必要的状态检查和写入，不做长时间 RPC、文件处理、大批量循环。
- 锁超时时间要覆盖正常业务 P99，并预留抖动空间；过短会提前释放，过长会影响故障恢复。

**风险边界**：

- Redis 主从异步复制下，主节点加锁后还没同步到从节点就宕机，新主可能没有这把锁。
- JVM 长时间 STW、网络分区、客户端超时重试，都可能让锁语义变弱。
- 因此核心一致性必须结合数据库唯一约束、乐观锁版本号、状态机、幂等表或补偿任务。

> [!WARNING]
> Redis 锁只能控制并发入口，不能替代数据库层面的最终一致性约束。

#### 面试 Q&A

**🧑‍💼 面试官**：你们 Redis 分布式锁怎么实现？

**🙋 您的话术**：
> “我们主要用 Redis + Redisson。自己实现时不会简单用 `SETNX`，而是用 `SET key value NX PX timeout`，保证加锁和设置过期时间是原子操作。value 会放请求唯一标识，释放锁时通过 Lua 脚本先判断 value 再删除，避免误删其他线程新加的锁。
> 
> Redisson 把可重入、Lua 原子释放、Watchdog 自动续期封装好了，所以生产更常用它。但我不会把 Redis 锁当成唯一一致性保障，核心场景还会加数据库唯一索引、状态机版本号或幂等表。”

### 4.5 Redis 限流与 Lua 原子操作

#### 核心知识

Redis 常用于分布式限流，因为它能在多个应用实例之间共享计数状态。限流的核心不是“拒绝用户”，而是在系统达到承载上限前，把风险控制在入口。

**常见限流算法**：

- **固定窗口**：实现简单，比如每分钟最多 100 次。但窗口边界可能突刺，上一分钟最后一秒和下一分钟第一秒叠加后瞬时流量翻倍。
- **滑动窗口**：按更细粒度统计最近一段时间请求，更平滑。Redis 可用 ZSET 保存请求时间戳。
- **令牌桶**：按固定速率生成令牌，请求拿到令牌才能通过，允许一定突发。
- **漏桶**：请求进入桶后按固定速率流出，更强调平滑处理。

**为什么用 Lua**：

- 限流通常包含多个步骤：删除过期窗口、统计数量、判断是否超过阈值、写入当前请求、设置过期时间。
- 如果这些步骤拆成多条 Redis 命令，并发下会出现竞态。
- Lua 脚本在 Redis 内部原子执行，可以保证这一组操作不会被其他命令插入。

**滑动窗口 ZSET 思路**：

1. `ZREMRANGEBYSCORE` 删除窗口外的旧请求。
2. `ZCARD` 统计窗口内请求数。
3. 如果未超过阈值，用 `ZADD` 写入当前时间戳和唯一请求 ID。
4. 设置 Key 过期时间，避免冷 Key 长期残留。

**工程注意点**：

- 限流 Key 要控制基数，如按用户、IP、接口、租户组合，避免无限膨胀。
- 限流失败要返回明确业务语义，如“请求过于频繁，请稍后再试”。
- Redis 限流本身也可能成为瓶颈，超高 QPS 场景要结合本地限流、网关限流、Sentinel 或 Nginx。
- 限流规则要能动态调整，突发活动时支持灰度放量和快速回滚。

## 5. Kafka 与异步消息架构

### 5.1 消息可靠性与防丢失

#### 核心知识

Kafka 不是简单的“消息队列”，它更像一个高吞吐、可持久化、可回放的分布式日志系统。面试时要先讲清楚它的基本模型，再讲防丢、顺序、重复和积压。

**核心模型**：

- **Topic**：消息的逻辑分类，比如订单事件、设备状态、用户行为。
- **Partition**：Topic 的物理分片。Kafka 的并行度、顺序性、存储分布都围绕 Partition 展开。
- **Offset**：消息在 Partition 内的递增位置。Kafka 不按消息 ID 消费，而是通过 offset 记录消费进度。
- **Broker**：Kafka 服务节点，负责存储和转发消息。
- **Producer**：消息生产者，把消息写入指定 Topic 的某个 Partition。
- **Consumer Group**：消费者组。同一组内，一个 Partition 同一时刻只能被一个消费者消费；不同组之间互不影响。

**为什么 Kafka 吞吐高**：

- 顺序写磁盘，避免大量随机 I/O。
- 利用 Page Cache，很多读写发生在操作系统缓存层。
- 批量发送和批量拉取，减少网络往返。
- 零拷贝 `sendfile`，减少用户态和内核态数据拷贝。
- Partition 并行，不同分区可以分布在不同 Broker 上。

**副本与 ISR**：

- 每个 Partition 可以有多个副本，其中一个是 Leader，其他是 Follower。
- Producer 和 Consumer 主要和 Leader 交互，Follower 从 Leader 拉取数据同步。
- ISR（In-Sync Replicas）是和 Leader 保持同步的副本集合。
- 如果 Follower 落后太多，会被踢出 ISR。
- `replication.factor` 决定副本数，常见生产配置是 3。

**Producer 防丢配置**：

- `acks=0`：发出去就认为成功，吞吐高但可能丢。
- `acks=1`：Leader 写入成功就返回，Leader 宕机且未同步给 Follower 时可能丢。
- `acks=all` / `-1`：Leader 等 ISR 副本确认后再返回，可靠性最高。
- `min.insync.replicas >= 2`：配合 `acks=all`，避免只有 Leader 一个副本时也返回成功。
- `retries` 和 `delivery.timeout.ms`：允许生产端遇到瞬时失败时重试。
- `enable.idempotence=true`：开启生产者幂等，避免重试导致单分区内重复写入。

**Broker 防丢重点**：

- 合理设置副本数，生产环境不要单副本承载核心消息。
- 监控 ISR 缩小、Leader 选举、磁盘使用率、请求延迟。
- 关键 Topic 不要允许不在 ISR 中的副本被选为 Leader，避免数据回退风险。

**Consumer 防丢重点**：

- 关闭自动提交 offset，业务处理成功后再手动提交。
- 如果先提交 offset 再处理业务，处理失败后消息不会再被消费，会丢。
- 如果业务处理成功但 offset 提交失败，消息会被再次消费，因此消费端必须幂等。
- Kafka 常见语义是 At-least-once，不轻易承诺 Exactly-once 到业务侧。

**消息语义**：

- **At-most-once**：最多一次，可能丢，不重复。
- **At-least-once**：至少一次，不丢但可能重复，生产最常见。
- **Exactly-once**：Kafka 事务可以在 Kafka 内部做到精确一次写入，但跨 DB、RPC、外部系统时仍要靠业务幂等和事务方案兜底。

### 5.2 顺序消费与重复消费

#### 核心知识

Kafka 的顺序性边界非常清楚：**只保证单 Partition 内消息有序，不保证 Topic 全局有序**。

**顺序消费设计**：

- 同一业务实体要使用同一个 Message Key，如 `orderId`、`deviceId`、`userId`。
- Kafka 默认会根据 Key 路由到固定 Partition，同一个 Key 的消息进入同一个 Partition。
- 单 Partition 内消息按 offset 顺序写入，也按 offset 顺序拉取。
- 如果业务要求同一个订单的创建、支付、发货严格有序，就要保证这些消息使用同一个订单号作为 Key。

**消费端破坏顺序的常见方式**：

- 消费线程从同一 Partition 拉取消息后，丢给公共线程池并发处理。
- 处理失败的消息异步重试，后续消息先执行成功，导致状态乱序。
- Rebalance 后没有正确处理未提交 offset，导致部分消息重复或顺序回退。

**业务维度有序方案**：

- 最简单是单 Partition 单线程消费，但吞吐有限。
- 更常用是按业务 Key Hash 到固定内存队列，同一个 Key 只在同一条队列串行处理。
- 对订单、支付、库存这类状态机业务，要在 DB 层增加状态版本或状态流转校验，防止乱序消息把状态回退。

**重复消费来源**：

- 消费成功但 offset 未提交，消费者宕机或 Rebalance 后会再次消费。
- Producer 重试、网络超时，可能导致消息重复写入。
- 死信重投、人工补偿、任务重放都可能带来重复。

**幂等设计**：

- 使用消息唯一 ID 建消费记录表，处理前先插入，唯一索引冲突说明已处理。
- 使用业务唯一约束，如订单号、支付流水号、退款单号。
- 使用状态机版本号，只有符合当前状态的消息才能推进状态。
- 对扣款、发券、库存扣减这类操作，不能只靠 Redis 去重，要有数据库约束兜底。

#### 面试 Q&A

**🧑‍💼 面试官**：订单创建、支付、发货消息不能乱序，Kafka 怎么设计？

**🙋 您的话术**：
> “Kafka 只能保证单分区有序，所以我们会把订单号作为 Message Key，让同一个订单的所有状态变更都路由到同一个 Partition。
> 
> 消费端不能再把同一个订单的消息随便丢给公共线程池并发处理，否则分区有序会被业务线程打乱。更稳的方式是单分区串行处理，或者按订单号 Hash 到固定队列，让同一个订单永远在同一条队列里串行执行。
> 
> 同时消费端会做幂等，比如订单状态机版本号、消息唯一表，防止重复消息导致状态回退或重复扣费。”

### 5.3 消息积压、Rebalance 与死信队列

#### 核心知识

消息积压不是一个单点问题，它说明“生产速度长期大于消费速度”。处理时不要第一反应就扩容消费者，要先判断瓶颈在哪里。

**Consumer Lag**：

- Lag = 最新 offset - 已提交消费 offset。
- Lag 持续上涨说明消费能力不足或消费者异常。
- Lag 短时上涨后能回落，通常是峰值流量；持续上涨才是容量问题。

**Rebalance 是什么**：

- Consumer Group 内消费者数量变化、Topic 分区变化、消费者心跳超时，都会触发 Rebalance。
- Rebalance 会重新分配 Partition，期间部分消费会暂停。
- 如果消费者处理时间过长，没有及时 poll 或心跳异常，可能被认为失活，导致频繁 Rebalance。

**关键参数**：

- `max.poll.records`：单次 poll 拉取的消息数量，太大可能导致处理超时，太小吞吐不足。
- `max.poll.interval.ms`：两次 poll 最大间隔，业务处理太慢超过这个值会触发 Rebalance。
- `session.timeout.ms` / `heartbeat.interval.ms`：消费者心跳相关参数。
- `fetch.min.bytes` / `fetch.max.wait.ms`：影响批量拉取效率和延迟。

**死信队列**：

- 对反复失败的消息设置最大重试次数。
- 超过重试次数后投递到死信 Topic，避免坏消息卡住整个 Partition。
- 死信消息要保留原 Topic、Partition、Offset、异常原因、重试次数，方便人工排查和补偿。

#### 工程实践

- 先看 Consumer Lag，再看单条消息耗时、错误率、下游 RT。
- 下游慢时不要盲目扩消费者，否则只是把压力继续打到下游。
- 分区数不足时，消费者实例再多也无法提升并行度。
- 单条坏消息持续失败，要进入死信队列，避免卡住分区。
- 长耗时任务要避免阻塞 Poll Thread，可采用内存队列 + 工作线程池 + pause/resume。

#### 面试 Q&A

**🧑‍💼 面试官**：Kafka 消费积压了怎么办？

**🙋 您的话术**：
> “我会先判断积压是短时峰值还是消费能力不足。第一步看 Consumer Lag、单条消息处理耗时、错误率和下游依赖 RT。
> 
> 如果是下游变慢，不会盲目扩消费者，因为扩了也只是把压力继续打到下游，应该先限流、降级或暂停消费。如果是消费者 CPU 或线程池不足，可以增加消费者实例，但前提是 Topic 分区数足够。
> 
> 如果是某个 Key 特别热导致单分区积压，要优化 Key 设计或拆分热点业务。对于一直失败的坏消息，设置重试上限，超过后投递死信队列，避免毒丸消息卡住整个分区。消费端必须幂等，因为扩容、重试、Rebalance 都可能带来重复消费。”

### 5.4 MQ 与最终一致性事务

#### 核心知识

跨服务强一致事务成本高，常用最终一致性。MQ 的价值不是让分布式事务消失，而是把跨服务同步调用拆成可重试、可补偿、可削峰的异步流程。

**本地消息表 / Outbox 模式**：

- 在业务库建一张消息表，记录待发送消息、状态、重试次数、下一次发送时间。
- 业务数据和消息记录在同一个本地事务里提交，保证“业务成功”和“消息可发送”原子绑定。
- 后台任务扫描消息表，把消息发送到 Kafka。
- Kafka ACK 成功后，把消息表状态更新为已发送。
- 如果发送失败，按重试策略继续投递。

**Binlog Outbox 方案**：

- 业务事务只写业务表和 outbox 表。
- 通过 Debezium、Canal 等监听 Binlog，把 outbox 变更投递到 Kafka。
- 优点是减少应用内定时扫描压力；缺点是引入 Binlog 订阅链路和运维复杂度。

**下游消费一致性**：

- 消费端必须幂等，因为 MQ 投递通常是 At-least-once。
- 消费端处理业务和记录消费状态最好放在同一个本地事务里。
- 如果下游调用外部系统，要保存调用状态和补偿任务，避免处理到一半丢状态。
- 最终一致性要有对账任务，定期扫描“业务成功但下游未完成”的异常单。

**适合 MQ 的场景**：

- 主链路削峰：下单成功后异步发券、发短信、同步数据。
- 跨服务解耦：订单服务不直接依赖多个下游服务同步成功。
- 事件驱动：用户行为、设备状态、风控事件广播。
- 最终一致性：本地事务 + 消息通知 + 下游幂等消费。

#### 追问防守

- Kafka 为什么吞吐高？顺序写、Page Cache、批量、零拷贝分别起什么作用？
- `acks=all` 为什么还要配 `min.insync.replicas`？
- Kafka 能保证消息不丢吗？Producer、Broker、Consumer 分别要怎么配？
- Kafka 为什么只能保证单 Partition 有序？
- 消费端多线程处理为什么可能破坏顺序？
- 重复消费有哪些来源，业务幂等怎么做？
- Consumer Lag 上涨时为什么不能只扩消费者？
- Rebalance 为什么会导致消费暂停或重复消费？
- 本地消息表如何保证业务操作和消息发送最终一致？

## 6. Spring Boot 核心原理

### 6.1 IOC、Bean 生命周期与依赖注入

#### 核心知识

Spring 的核心不是“用了注解”，而是把对象创建、依赖装配、生命周期管理、扩展点执行都交给容器统一完成。

**IOC 与 DI**：

- IOC（控制反转）：对象不再由业务代码手动 `new`，而是由 Spring 容器创建和管理。
- DI（依赖注入）：对象依赖的其他组件由容器注入，业务类只声明依赖，不负责查找和组装。
- 好处是降低耦合、统一生命周期、便于测试、便于 AOP 增强。

**BeanFactory 与 ApplicationContext**：

- `BeanFactory` 是基础容器，提供 Bean 定义、创建、获取能力。
- `ApplicationContext` 是增强容器，在 `BeanFactory` 基础上增加国际化、事件发布、资源加载、环境配置、自动预实例化单例 Bean 等能力。
- Spring Boot 应用里通常使用 `ApplicationContext`，很少直接使用 `BeanFactory`。

**BeanDefinition**：

- Spring 不是一开始就直接创建对象，而是先把类、作用域、构造方法、属性、初始化方法等信息解析成 `BeanDefinition`。
- XML、注解、Java Config 最终都会变成容器里的 BeanDefinition。
- 后续 Bean 创建就是根据 BeanDefinition 进行实例化、依赖注入和初始化。

**Bean 生命周期主线**：

1. 扫描或读取配置，生成 BeanDefinition。
2. 实例化 Bean，对象被创建出来，但依赖还没填充。
3. 属性填充，注入依赖 Bean。
4. 执行 Aware 回调，如 `BeanNameAware`、`ApplicationContextAware`。
5. 执行 `BeanPostProcessor#postProcessBeforeInitialization`。
6. 执行初始化方法，如 `@PostConstruct`、`InitializingBean`、自定义 init-method。
7. 执行 `BeanPostProcessor#postProcessAfterInitialization`，AOP 代理通常在这里生成。
8. Bean 进入可用状态。
9. 容器关闭时执行销毁方法，如 `@PreDestroy`、`DisposableBean`、destroy-method。

**BeanPostProcessor 的意义**：

- 它是 Spring 最重要的扩展点之一，可以在 Bean 初始化前后插入逻辑。
- AOP、`@Autowired`、`@Value`、`@PostConstruct` 等很多能力都依赖不同的后置处理器。
- 面试时可以说：Spring 很多“魔法”本质上不是魔法，而是容器启动过程中一批扩展点按顺序生效。

**依赖注入方式**：

- 构造器注入：推荐。依赖明确、可声明 `final`、对象创建后就是完整状态，也更利于单元测试。
- Setter 注入：适合可选依赖或运行期可变配置。
- 字段注入：写起来简单，但隐藏依赖，不利于测试，也不利于不可变设计。

**循环依赖**：

- Spring 通过三级缓存解决部分单例 Bean 的循环依赖，主要是 setter/字段注入场景。
- 构造器循环依赖无法解决，因为两个对象都必须先构造完成才能注入对方。
- 原型 Bean 循环依赖也不适合依赖三级缓存解决。
- 三级缓存还能解决 AOP 提前暴露代理对象的问题，否则注入进去的可能是原始对象，不是代理对象。

**作用域**：

- `singleton`：默认作用域，一个容器一个实例。
- `prototype`：每次获取都创建新实例，容器不完整管理销毁。
- Web 场景还有 `request`、`session`、`application` 等作用域。

### 6.2 AOP 与动态代理

#### 核心知识

AOP 用于把日志、权限、事务、监控、审计这类横切逻辑从业务代码中抽离出来。它的核心思想是：业务方法只关心业务，通用增强逻辑由代理对象在方法前后织入。

**核心概念**：

- **Join Point**：连接点，Spring AOP 中主要指方法执行点。
- **Pointcut**：切点，定义哪些方法需要被增强。
- **Advice**：通知，定义增强逻辑，如前置、后置、环绕、异常通知。
- **Aspect**：切面，切点 + 通知的组合。
- **Proxy**：代理对象，外部调用实际进入代理对象，再由代理对象调用目标对象。

**两种代理方式**：

- **JDK 动态代理**：基于接口生成代理类，目标类需要实现接口。
- **CGLIB 代理**：基于继承生成目标类子类，不要求接口。
- Spring Boot 默认更倾向使用 CGLIB，但具体行为和配置、版本有关。
- `final` 类无法被 CGLIB 继承，`final` 方法无法被子类重写，因此无法正常增强。

**AOP 生效边界**：

- 必须通过 Spring 容器管理的 Bean 调用。
- 必须从代理对象进入方法，内部 `this.method()` 调用会绕过代理。
- private 方法、final 方法、静态方法通常不能被 Spring AOP 正常代理增强。
- 同一个类里注解方法互调，是事务、缓存、异步注解失效的高发原因。

**常见注解背后的 AOP**：

- `@Transactional`：事务开启、提交、回滚。
- `@Cacheable` / `@CacheEvict`：缓存读取和删除。
- `@Async`：异步执行，本质也是通过代理切换到线程池。
- 自定义权限、审计、日志注解，也常用 AOP 实现。

**环绕通知的价值**：

- `@Around` 可以控制方法是否执行、何时执行、执行前后做什么。
- 常用于接口耗时统计、参数审计、限流、统一异常包装。
- 但不要在切面里塞复杂业务逻辑，否则会让调用链变隐蔽，排查困难。

### 6.3 `@Transactional` 事务失效

#### 常见场景

- 同类内部 `this.method()` 调用，绕过代理。
- 方法不是 `public`。
- 异常被 catch 后没有继续抛出。
- checked 异常默认不回滚，需要 `rollbackFor = Exception.class`。
- 事务方法里放远程调用，导致连接持有时间过长。
- 数据库引擎不支持事务，比如 MyISAM。
- 事务方法所在类没有交给 Spring 容器管理，或者手动 `new` 了对象。
- 多线程里调用事务方法，线程切换后事务上下文不会自动传播。
- `@Transactional` 标在 private/final 方法上，代理无法增强。
- 传播行为配置不当，比如内部方法使用 `REQUIRES_NEW` 导致事务边界和预期不一致。

#### 核心知识

Spring 事务的底层是 AOP + 事务管理器。代理对象在方法执行前开启事务，方法正常返回则提交，抛出符合回滚规则的异常则回滚。

**事务传播行为**：

- `REQUIRED`：默认。当前有事务就加入，没有就新建。
- `REQUIRES_NEW`：挂起当前事务，创建新事务。适合审计日志、独立流水，但要注意连接资源消耗。
- `NESTED`：嵌套事务，依赖保存点，外层回滚会影响内层。
- `SUPPORTS`：有事务就加入，没有就非事务执行。
- `NOT_SUPPORTED`：以非事务方式执行，并挂起当前事务。

**回滚规则**：

- 默认只对 `RuntimeException` 和 `Error` 回滚。
- checked 异常默认不回滚，需要配置 `rollbackFor = Exception.class`。
- 异常被 catch 后不抛出，事务拦截器认为方法成功，会提交事务。
- 如果必须 catch，要么继续抛出，要么手动 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`。

**事务边界设计**：

- 事务范围越小越好，只包数据库一致性操作。
- 不要在事务中做远程 HTTP/RPC/MQ 同步等待，避免长时间占用数据库连接和锁。
- 查询大列表、文件处理、复杂计算不要放进事务。
- 核心写链路要结合唯一索引、乐观锁、状态机，而不是只依赖事务注解。

#### 面试 Q&A

**🧑‍💼 面试官**：你遇到过 `@Transactional` 不生效吗？

**🙋 您的话术**：
> “遇到过，最典型的是同一个类里方法互调。Spring 声明式事务是 AOP 代理实现的，外部调用 Bean 方法会经过代理对象，代理对象负责开启、提交或回滚事务。但如果类内部用 `this.xxx()` 调另一个带事务的方法，就绕过代理，事务不会生效。
> 
> 另一个常见问题是异常被 catch 掉。Spring 默认根据未捕获的运行时异常回滚，如果 catch 后只打印日志不抛出，事务管理器会认为方法正常结束。
> 
> 我们一般把事务边界放到独立 Service，通过 Spring Bean 外部调用；异常要继续抛出或手动标记回滚；涉及 checked 异常时显式配置 `rollbackFor = Exception.class`。事务里也尽量不做远程调用，避免数据库连接被长时间占用。”

### 6.4 自动配置与 Starter 机制

#### 核心知识

Spring Boot 的核心价值是把 Spring 应用的通用装配流程标准化：引入 Starter、写少量配置、自动创建合适的 Bean。

**`@SpringBootApplication` 组成**：

- `@SpringBootConfiguration`：本质是配置类。
- `@ComponentScan`：扫描当前包及子包下的组件。
- `@EnableAutoConfiguration`：开启自动配置，是 Spring Boot 开箱即用的核心。

**自动配置加载机制**：

- Spring Boot 2 主要通过 `META-INF/spring.factories` 声明自动配置类。
- Spring Boot 3 主要通过 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports` 声明自动配置类。
- 启动时框架读取这些候选自动配置类，再根据条件注解决定是否生效。

**条件注解**：

- `@ConditionalOnClass`：classpath 中存在某个类才生效。
- `@ConditionalOnMissingBean`：容器中没有用户自定义 Bean 时才创建默认 Bean。
- `@ConditionalOnProperty`：配置项满足条件才生效。
- `@ConditionalOnBean`：容器中存在某个 Bean 才生效。
- `@ConditionalOnWebApplication`：当前是 Web 应用才生效。

**Starter 是什么**：

- Starter 本身通常不写太多业务代码，而是把一组依赖、自动配置类、配置属性组织在一起。
- 例如引入 Web Starter，会带来 Spring MVC、Tomcat、JSON 序列化等依赖和配置。
- 引入 Redis Starter，会让 Spring Boot 根据 classpath 和配置自动创建连接工厂、RedisTemplate 等 Bean。

**配置绑定**：

- `@ConfigurationProperties` 可以把 `application.yml` 中的配置绑定到 Java 对象。
- 相比到处使用 `@Value`，配置属性类更适合复杂配置、可校验、可提示。

**自动配置的优先级思想**：

- 框架提供默认 Bean，让应用快速启动。
- 用户自定义 Bean 优先，自动配置通过 `@ConditionalOnMissingBean` 让位。
- 这就是 Spring Boot “约定大于配置，但允许覆盖约定”的关键。

**排查自动配置问题**：

- 看启动日志和 Condition Evaluation Report。
- 检查 classpath 是否缺少依赖。
- 检查配置项是否写错。
- 检查是否已经存在同类型 Bean，导致默认自动配置没有生效。

#### 追问防守

- BeanFactory 和 ApplicationContext 有什么区别？
- Bean 生命周期里 BeanPostProcessor 在什么时候执行？
- Spring 为什么能解决部分循环依赖，为什么构造器循环依赖解决不了？
- AOP 为什么同类内部调用会失效？
- JDK 动态代理和 CGLIB 的区别是什么？
- `@Transactional` 为什么异常被 catch 后不会回滚？
- `REQUIRED` 和 `REQUIRES_NEW` 有什么区别？
- Spring Boot 自动配置为什么不会覆盖用户自定义 Bean？
- Starter、自动配置类、条件注解之间是什么关系？

#### 面试 Q&A

**🧑‍💼 面试官**：Spring Boot 自动配置怎么实现？

**🙋 您的话术**：
> “Spring Boot 开箱即用的核心是自动配置。启动时它会从依赖包里扫描自动配置清单，把候选配置类加载进来。但这些配置类不会全部生效，而是通过大量条件注解判断。
> 
> 比如 `DataSourceAutoConfiguration` 会判断 classpath 里有没有 `DataSource`、连接池、数据库驱动，同时判断容器里是否已经有用户自定义的 Bean。如果条件满足，才会根据 `application.yml` 创建数据源。
> 
> 这套机制让开发者只要引入 Starter 和少量配置，就能完成复杂 Bean 装配。”

## 7. 微服务治理与稳定性设计

### 7.1 Nacos 注册中心与配置中心

#### 核心知识

微服务治理的第一步是让服务能被发现、能被调用、能被动态调整。注册中心解决“服务在哪里”，配置中心解决“运行参数如何动态变更”。

**注册中心职责**：

- 服务实例启动时向注册中心注册 IP、端口、服务名、元数据。
- 调用方通过服务名获取可用实例列表。
- 注册中心通过心跳或健康检查判断实例是否可用。
- 实例下线、宕机、网络异常时，注册中心要及时摘除或标记不可用。

**Nacos 实例类型**：

- **临时实例**：通过心跳续约，心跳超时后自动摘除，适合大多数应用服务实例。
- **持久实例**：实例信息长期保留，更多依赖服务端探活，适合某些固定基础设施节点。

**配置中心职责**：

- 管理不同环境、不同服务、不同租户的配置。
- 支持动态刷新，如限流阈值、降级开关、灰度比例、外部接口超时时间。
- 支持配置版本、发布记录、回滚和权限控制。

**配置治理原则**：

- 生产配置变更要有审批、发布记录和回滚方案。
- 高风险配置要灰度，不要直接全量推送。
- 配置项要有默认值、边界校验和单位说明，比如毫秒/秒、QPS/并发数。
- 动态配置不能滥用。数据库表结构、核心状态机规则这类强一致逻辑，不应随意通过配置热更新。

**常见风险**：

- 注册中心短时不可用时，本地缓存服务列表要能继续工作。
- 实例摘除不及时会导致请求打到异常节点。
- 配置误推可能比代码 Bug 影响更快，需要灰度和回滚。
- 配置刷新后要观察指标，确认错误率、RT、限流量是否符合预期。

### 7.2 超时、重试、幂等

#### 核心知识

超时、重试、幂等是微服务调用里最基础也最容易踩坑的三件事。它们不是单独配置，而是一组联动策略。

**超时设计**：

- 每一层都要有明确超时：网关、Controller、RPC、HTTP Client、数据库、Redis、MQ、线程池任务。
- 超时时间要自上而下收敛，不能下游超时比上游还长。例如网关 3s，业务接口 2.5s，下游 HTTP 1s。
- 没有超时的远程调用会长期占用 Tomcat 线程、业务线程池、连接池，最终拖垮整个服务。
- 超时不是越短越好，要结合下游 P99、业务容忍度和重试成本设置。

**重试设计**：

- 重试只适合瞬时失败，如网络抖动、连接重置、短暂 503。
- 重试必须有限次数，配合指数退避和随机抖动，避免所有请求同时重试形成流量尖峰。
- 重试要有总耗时预算，不能单次超时 1s、重试 3 次，结果上游 2s 早已超时。
- 不要在多层同时重试。网关、RPC、业务代码都重试，会放大成重试风暴。

**幂等设计**：

- 查询天然幂等，写请求不一定幂等。
- 创建订单、支付、发券、扣库存这类写请求，必须用幂等键、唯一索引、状态机、去重表保护。
- 幂等键可以来自业务唯一号，如订单号、支付流水号，也可以由客户端生成请求号。
- 幂等结果要可查询：重复请求进来时，应返回第一次处理结果，而不是重新执行副作用。

**调用失败分类**：

- 明确失败：下游返回业务错误，通常不重试。
- 超时未知：下游可能成功也可能失败，需要通过幂等查询、状态确认、补偿任务处理。
- 系统失败：连接失败、服务不可用，可有限重试或快速失败。

#### 面试 Q&A

**🧑‍💼 面试官**：服务调用失败时，是直接重试吗？

**🙋 您的话术**：
> “不会无脑重试。重试本质是在故障时放大流量，如果没有限制，很容易从局部慢调用变成全链路雪崩。
> 
> 我们会先区分请求类型。查询类、幂等写类可以做有限重试，并加指数退避和随机抖动；非幂等写请求，比如扣款、发券、创建订单，必须先有幂等键或状态机保护，否则宁可快速失败也不能随便重试。
> 
> 同时我们会设置完整超时链路，避免线程长期阻塞。连续失败或慢调用比例超过阈值后，熔断器打开，后续请求直接 fallback，不再继续打下游。”

### 7.3 熔断、限流、降级

#### 核心知识

限流、熔断、降级是稳定性保护的三件套。它们解决的问题不一样：限流管入口，熔断管依赖，降级管体验和核心链路。

**限流**：

- 目标是控制进入系统的流量，保护自己和下游。
- 常见维度：接口 QPS、用户维度、IP 维度、租户维度、热点参数、并发线程数。
- 常见位置：网关限流、应用限流、单机限流、Redis 分布式限流。
- 限流不是简单拒绝，要给出业务可接受的响应，如排队、稍后重试、降级页面。

**熔断**：

- 目标是下游持续异常时快速失败，避免调用方线程池被拖死。
- 常见触发条件：异常比例、慢调用比例、连续失败次数。
- 熔断器通常有关闭、打开、半开三个状态。
- 半开状态放少量探测请求，如果恢复则关闭熔断，否则继续打开。

**降级**：

- 目标是在资源不足或依赖异常时牺牲非核心能力，保障核心链路。
- 常见方式：返回缓存、默认值、空结果、静态文案、排队提示、关闭非核心模块。
- 降级方案要提前设计，不能故障时临时想。
- 降级结果要符合业务预期，不能为了“不报错”返回误导性数据。

**Sentinel 常用能力**：

- QPS 限流。
- 并发线程数限流。
- 热点参数限流。
- 慢调用比例熔断。
- 异常比例 / 异常数熔断。
- 规则动态推送和控制台观察。

**隔离设计**：

- 线程池隔离：不同业务、不同下游使用不同线程池，避免互相拖垮。
- 连接池隔离：核心库、报表库、外部接口连接池隔离。
- 舱壁模式：一个模块出问题，只影响自己的资源池，不扩散到全站。

#### 工程实践

- 大促或突发流量前配置限流阈值和降级开关。
- 下游接口必须有超时和熔断，不能无限等待。
- 降级结果要符合业务预期，比如返回缓存、默认值、稍后重试提示。
- 核心链路和非核心链路资源隔离，如下单、支付、通知、报表不要共用关键线程池。
- 限流、熔断、降级规则要接入配置中心，支持灰度、回滚和审计。

### 7.4 可观测性：日志、指标、链路追踪

#### 核心知识

可观测性不是“出了问题看日志”，而是在故障发生前能发现趋势，故障发生时能快速定位，故障恢复后能复盘验证。

**三件套**：

- **日志（Logging）**：还原单次请求发生了什么，适合查具体错误、参数、异常堆栈。
- **指标（Metrics）**：观察系统趋势，适合告警和容量判断，如 QPS、RT、错误率。
- **链路追踪（Tracing）**：还原跨服务调用链路，定位慢在哪个服务、哪个依赖、哪个方法。

**核心指标**：

- 入口层：QPS、并发数、P95/P99 RT、错误率、限流数。
- JVM：堆内存、非堆、GC 次数和耗时、线程数、CPU。
- 线程池：核心线程数、活跃线程数、队列长度、拒绝次数、任务耗时。
- 数据库：连接池活跃数、等待数、慢 SQL、锁等待、主从延迟。
- Redis：命中率、RT、慢命令、大 Key、内存、连接数。
- Kafka：Consumer Lag、消费速率、失败数、Rebalance 次数、死信数量。
- 下游依赖：调用量、成功率、超时率、P99 RT。

**TraceId 传播**：

- TraceId 要从网关进入系统开始生成或透传。
- HTTP/RPC 调用要通过 Header 传递。
- MQ 消息要把 TraceId 放进消息 Header 或消息体元数据。
- 异步线程池要显式传递上下文，避免 TraceId 断链。

**日志原则**：

- 关键链路记录业务 ID，如 orderId、userId、requestId，方便串联。
- 错误日志要包含异常堆栈和关键上下文，不要只打印“操作失败”。
- 避免打印敏感信息，如身份证、手机号明文、Token、密码。
- 高频日志要控制采样和级别，避免日志把磁盘和 IO 打满。

**告警原则**：

- 告警要有业务含义，不能只报机器 CPU 高。
- 告警要分级：提示、警告、严重、灾难。
- 告警要能指向处理动作，如扩容、降级、回滚、联系下游。
- 要避免告警风暴，同一根因触发多条告警时要聚合。

### 7.5 发布、回滚与故障复盘

#### 工程实践

- 灰度发布，先小流量验证再全量。
- 关键配置可动态调整，但要有审批和回滚。
- 故障复盘关注时间线、影响面、根因、止血动作、长期改进。

**发布策略**：

- 蓝绿发布：两套环境切流，回滚快，但资源成本高。
- 滚动发布：逐批替换实例，资源利用高，但发布期间新旧版本共存。
- 金丝雀发布：先放少量真实流量，观察指标后逐步放量。
- 灰度发布：按用户、租户、地区、版本等维度放量。

**发布前检查**：

- 数据库变更是否兼容旧代码和新代码。
- 配置项是否有默认值和回滚值。
- 是否有监控大盘和核心告警。
- 是否准备降级开关和回滚方案。
- 是否评估缓存、MQ、定时任务、异步消费的兼容性。

**回滚原则**：

- 代码可回滚，数据不一定能回滚，所以数据库变更要特别谨慎。
- 先止血，再定位。故障中不要执着于立刻找根因。
- 回滚后要继续观察错误率、RT、积压、连接池、数据库压力是否恢复。

**故障复盘**：

- 时间线：从变更、告警、发现、定位、止血、恢复完整梳理。
- 影响面：影响哪些用户、接口、订单、金额、时长。
- 根因：技术根因和流程根因都要写清楚。
- 止血动作：限流、降级、扩容、回滚、修数据。
- 长期改进：监控补齐、压测补齐、预案补齐、代码和流程改造。

- 注册中心不可用时，服务调用一定会全部失败吗？为什么本地缓存很重要？
- 配置中心为什么要灰度和回滚？配置误推有什么风险？
- 超时、重试、熔断之间怎么配合？
- 为什么不能多层都重试？什么是重试风暴？
- 幂等键、唯一索引、状态机分别解决什么问题？
- 限流、熔断、降级的区别是什么？
- 线程池隔离和舱壁模式解决什么问题？
- 日志、指标、链路追踪分别用于什么场景？

#### 面试收口话术

> “我理解的微服务治理不是堆组件，而是让系统在异常情况下可控失败。正常时要有监控和容量评估，流量异常时要有限流和降级，下游异常时要有超时和熔断，数据重复时要有幂等，故障后要能通过日志、指标、链路追踪快速定位，并通过复盘把问题沉淀成规则。”

## 8. Netty 与高性能网络通信

### 8.1 BIO、NIO 与 Reactor 模型

#### 核心知识

Netty 不是普通的网络工具包，而是一个基于 Java NIO 的高性能网络通信框架。很多 RPC、网关、MQ、长连接推送系统都会用到 Netty 或类似的事件驱动模型。

面试讲 Netty 时，不要一上来背类名，先讲清楚它解决的问题：传统阻塞 IO 在高并发连接下线程成本高、上下文切换多、资源利用率低；Netty 通过非阻塞 IO、事件驱动、线程模型和内存管理，把网络连接、读写事件、编解码、业务处理组织成可扩展的架构。

**BIO 模型**：

- 一个连接通常对应一个线程，读写阻塞。
- 连接数少、并发低时简单直接。
- 高并发长连接场景下会产生大量线程，内存、调度和上下文切换成本很高。

**NIO 模型**：

- 基于 `Channel`、`Buffer`、`Selector`。
- 一个线程可以通过 Selector 监听多个 Channel 的连接、读、写事件。
- 线程不需要阻塞等待某一个连接的数据，适合大量连接、少量活跃的场景。

**Reactor 模型**：

- Reactor 本质是事件分发模型：监听 IO 事件，事件就绪后分发给对应 Handler 处理。
- 单 Reactor 单线程：所有连接、读写、业务处理都在一个线程，模型简单但容易被业务阻塞。
- 单 Reactor 多线程：IO 事件由 Reactor 处理，业务逻辑丢给工作线程池。
- 主从 Reactor 多线程：主 Reactor 负责接收连接，从 Reactor 负责读写事件，业务线程池负责耗时业务。

**Netty 的线程模型**：

- `bossGroup`：负责接收客户端连接，处理 `accept` 事件。
- `workerGroup`：负责连接建立后的读写事件。
- 一个 `EventLoop` 绑定一个线程，一个 Channel 注册到某个 EventLoop 后，后续 IO 事件通常都由这个 EventLoop 处理。
- 同一个 Channel 的事件在同一个 EventLoop 中串行执行，降低并发锁竞争。

可以这样理解：Netty 用少量 IO 线程管理大量连接，把“一个连接一个线程”的模型改成“一个线程管理多个连接的事件”。

### 8.2 EventLoop、ChannelPipeline 与 Handler

#### 核心知识

Netty 的核心抽象可以按一条请求的流转来理解：连接进来形成 Channel，Channel 注册到 EventLoop，读写事件经过 ChannelPipeline，Pipeline 上的一组 Handler 依次完成编解码、鉴权、业务处理、异常处理和写回响应。

**EventLoop**：

- 本质是一个事件循环线程，负责处理注册在它上面的 Channel IO 事件。
- 除了 IO 事件，也可以执行普通任务和定时任务。
- 不要在 EventLoop 里执行耗时阻塞操作，如数据库查询、远程 HTTP、复杂文件处理。
- 如果业务逻辑耗时，要投递到独立业务线程池，否则一个 EventLoop 被卡住，会影响它负责的所有连接。

**Channel**：

- 表示一个网络连接或网络端点。
- 服务端常见的是 `NioServerSocketChannel`，客户端连接常见的是 `NioSocketChannel`。
- Channel 负责读写数据，但真正的处理逻辑由 Pipeline 和 Handler 编排。

**ChannelPipeline**：

- 可以理解为处理链，内部维护多个 `ChannelHandler`。
- 入站事件从头到尾传播，如连接建立、读到数据、异常。
- 出站事件通常从尾到头传播，如写响应、flush、关闭连接。
- 编解码、日志、心跳、鉴权、业务处理都可以拆成独立 Handler，便于组合和复用。

**ChannelHandler**：

- `ChannelInboundHandler` 处理入站事件，如 `channelRead`、`channelActive`、`exceptionCaught`。
- `ChannelOutboundHandler` 处理出站事件，如 `write`、`flush`。
- Handler 里要避免阻塞 EventLoop。
- 如果 Handler 有共享状态，要特别注意线程安全；标了 `@Sharable` 的 Handler 才适合被多个 Channel 复用。

**典型处理链**：

- `IdleStateHandler`：心跳空闲检测。
- Frame Decoder：解决拆包粘包，按协议边界切分消息。
- Message Decoder：把字节流反序列化成业务对象。
- Auth Handler：鉴权、校验 token、校验签名。
- Business Handler：执行业务逻辑。
- Message Encoder：把响应对象序列化成字节。
- Exception Handler：统一异常处理和连接关闭。

#### 工程实践

- IO 线程只做轻量处理，耗时业务进入业务线程池。
- Pipeline 职责要清晰，编解码、鉴权、业务、异常处理不要揉在一个 Handler 里。
- 对于长连接系统，要记录连接数、活跃连接数、连接建立/断开原因。
- Handler 异常要及时捕获，必要时关闭异常连接，避免连接半死不活。

### 8.3 ByteBuf、零拷贝与内存管理

#### 核心知识

Netty 性能高，一个重要原因是它对内存和数据拷贝做了大量优化。面试时要能讲清楚 ByteBuf 为什么比 Java 原生 ByteBuffer 更好用，以及堆外内存为什么既能提升性能也可能带来泄漏风险。

**ByteBuf 的特点**：

- 使用 `readerIndex` 和 `writerIndex` 区分读写位置，不需要像 `ByteBuffer` 那样频繁 `flip()`。
- 支持自动扩容、切片、引用计数、池化分配。
- 支持堆内内存和堆外直接内存。

**堆内内存与堆外内存**：

- 堆内内存由 JVM GC 管理，分配和回收更直观，但网络 IO 可能需要额外拷贝到内核缓冲区。
- 堆外直接内存减少一次 JVM 堆到直接内存的拷贝，适合高性能网络通信。
- 堆外内存不在 Java 堆里，监控堆内存不高不代表进程内存安全，RSS 可能持续上涨。

**引用计数**：

- Netty 的部分 ByteBuf 通过引用计数管理生命周期。
- `retain()` 增加引用计数，`release()` 减少引用计数。
- 引用计数归零后内存可被回收或归还池化分配器。
- 如果该释放不释放，会造成堆外内存泄漏；如果提前释放，后续访问可能出现非法访问异常。

**零拷贝思想**：

- Netty 的零拷贝更多是用户态层面的减少拷贝，不等于所有场景都完全没有内存复制。
- `slice()` / `duplicate()` 可以基于同一块内存创建视图，避免复制字节数组。
- `CompositeByteBuf` 可以把多个 ByteBuf 组合成逻辑上的连续缓冲区。
- 文件传输可使用 `FileRegion` 利用操作系统能力减少拷贝。

**池化分配**：

- Netty 默认可使用池化 ByteBuf 分配器，减少频繁分配和释放带来的开销。
- 池化提升性能，但也让内存问题更隐蔽，需要配合监控和泄漏检测。

#### 线上风险

- ByteBuf 未释放导致堆外内存泄漏，现象可能是 Java 堆不高，但进程内存持续上涨，最后容器 OOM Kill。
- 大包或恶意请求导致 ByteBuf 扩容过大，占用大量直接内存。
- 业务线程长期持有 ByteBuf，导致内存无法归还池化分配器。
- 日志打印完整报文，既拖慢 IO，又可能造成敏感信息泄露。

### 8.4 粘包拆包、编解码与协议设计

#### 核心知识

TCP 是字节流协议，不保留应用层消息边界。发送方写了两次，接收方可能一次读到；发送方写了一次，接收方也可能分多次读到。这就是粘包和拆包问题。

**产生原因**：

- TCP 面向字节流，不知道业务消息边界。
- Nagle 算法、操作系统缓冲区、网络拥塞、接收端读取速度都会影响数据聚合和拆分。
- 应用层如果没有明确协议边界，就无法稳定还原消息。

**常见解决方案**：

- 固定长度协议：每个消息长度固定，简单但浪费空间，不灵活。
- 分隔符协议：用 `\n` 或特殊字符分隔，适合文本协议，但要处理转义和内容冲突。
- 长度字段协议：消息头里放 body 长度，接收端先读长度再读指定字节，通用性最好。
- TLV 协议：Type、Length、Value，便于扩展字段和兼容多种消息类型。

**Netty 常见 Decoder**：

- `FixedLengthFrameDecoder`：固定长度拆包。
- `DelimiterBasedFrameDecoder`：按分隔符拆包。
- `LineBasedFrameDecoder`：按行拆包。
- `LengthFieldBasedFrameDecoder`：按长度字段拆包，是自定义二进制协议里最常用的方案。

**协议设计要点**：

- 魔数：快速判断是否是合法协议，避免误解析。
- 版本号：支持协议升级和兼容。
- 序列化类型：JSON、Protobuf、Hessian 等。
- 消息类型：请求、响应、心跳、推送、错误。
- 请求 ID：支持异步请求响应匹配。
- 长度字段：明确 body 大小，解决消息边界。
- 校验或签名：防篡改、防非法请求。

#### 工程实践

- 一定要限制单包最大长度，避免超大包打爆内存。
- 解码失败要快速关闭连接或返回协议错误，不能继续读脏数据。
- 协议字段要保留扩展空间，避免后续升级只能推翻重来。
- 请求 ID 要全链路透传，方便日志和链路追踪。

### 8.5 心跳、连接治理与线上排障

#### 核心知识

Netty 常用于长连接场景，如 IM、推送、网关、RPC 连接池。长连接系统不只是“连上就行”，更重要的是连接生命周期治理。

**为什么需要心跳**：

- TCP 连接可能因为网络中断、NAT 超时、客户端崩溃变成半连接。
- 服务端如果不主动检测，会一直保留无效连接，占用内存和连接资源。
- 心跳可以判断连接是否活跃，也可以维持 NAT 映射。

**心跳设计**：

- 客户端定时发送 ping，服务端回复 pong。
- 服务端通过 `IdleStateHandler` 检测读空闲、写空闲、读写空闲。
- 连续多次心跳失败后关闭连接，释放资源。
- 心跳间隔不能太短，否则会增加无意义流量；也不能太长，否则异常连接释放太慢。

**连接治理**：

- 限制单机最大连接数，超过阈值要拒绝或迁移。
- 按用户、设备、租户记录连接关系，支持踢下线、重连、消息路由。
- 客户端重连要有退避和随机抖动，避免服务端恢复后所有客户端同时重连。
- 服务端发布或扩容时，要考虑连接迁移、优雅关闭和流量摘除。

**常见排障指标**：

- 连接数、活跃连接数、连接建立速率、断开速率。
- EventLoop 任务队列长度、执行耗时、阻塞次数。
- 入站/出站流量、消息包大小、解码失败数。
- 堆外内存、ByteBuf 泄漏告警、进程 RSS。
- 心跳超时数、重连次数、连接关闭原因。

**常见问题定位**：

- 连接数暴涨：看是否客户端重连风暴、网关转发异常、连接未释放。
- RT 突然变高：看 EventLoop 是否被阻塞，业务是否在 IO 线程里执行。
- 进程内存上涨：看直接内存、ByteBuf release、是否有大包或池化内存长期占用。
- 消息解析失败：看协议版本、长度字段、序列化方式、半包处理。
- 频繁断连：看心跳配置、网络抖动、NAT 超时、服务端主动关闭原因。

#### 面试 Q&A

**🧑‍💼 面试官**：Netty 为什么性能高？

**🙋 您的话术**：
> “Netty 性能高不是靠某一个点，而是一整套设计。第一，它基于 NIO 和 Reactor 模型，用少量 EventLoop 线程管理大量连接，避免一个连接一个线程的资源浪费。第二，ChannelPipeline 把编解码、业务处理、异常处理拆成事件链，IO 线程可以高效分发。第三，ByteBuf 支持池化、堆外内存和引用计数，减少频繁分配和数据拷贝。
> 
> 但线上用 Netty 也要注意风险，EventLoop 不能被阻塞，ByteBuf 要正确释放，协议要处理粘包拆包并限制最大包大小，长连接还要有心跳、重连退避和连接数监控。”

**🧑‍💼 面试官**：Netty 的 EventLoop 为什么不能做耗时业务？

**🙋 您的话术**：
> “因为 EventLoop 是复用线程，一个 EventLoop 通常负责多个 Channel 的 IO 事件。如果在 `channelRead` 里直接查数据库、调外部接口或做复杂计算，这个 EventLoop 就会被卡住，它负责的所有连接都不能及时读写，表现出来就是一批连接 RT 变高、心跳超时甚至断连。
> 
> 正确做法是 IO 线程只做轻量的解码、校验和分发，把耗时业务投递到独立业务线程池，处理完再把结果写回 Channel。同时要监控 EventLoop 队列长度和任务耗时。”
