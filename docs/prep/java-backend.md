## 1. 并发编程与底层 (JUC)

### 1.1 线程池深度机制与背压流转
在处理高并发请求时，线程池的参数配置和任务流转逻辑至关重要。
当提交新任务时，流转逻辑如下：
1. 若当前运行的线程数小于 `corePoolSize`，则直接创建新核心线程执行任务。
2. 若达到 `corePoolSize`，新任务放入 `workQueue` (如阻塞队列)。
3. 若 `workQueue` 已满，且运行线程数小于 `maximumPoolSize`，则创建非核心线程执行任务。
4. 若均已达到上限，则触发**拒绝策略**。

> [!TIP]
> 最佳实践：在应对突发流量洪峰时，我们通常不建议使用丢弃策略 (`AbortPolicy` 或 `DiscardPolicy`)。采用 `CallerRunsPolicy` 可以有效实现**背压 (Backpressure)** 机制。当线程池满载时，将任务退回给调用者（如 Tomcat 线程）去执行，这样不仅保证了任务不丢失，同时也限制了上游请求的接收速度，防止系统彻底崩溃。

### 1.2 分布式锁选型：Redis vs ZooKeeper
分布式锁是微服务中保证数据一致性的核心组件，常见的选型主要是 Redis 和 ZooKeeper。

- **Redis 分布式锁**：通常基于 AP 模型。性能极高，适合高并发场景。
  - **核心机制**：利用 `SET resource_name my_random_value NX PX 30000` 保证互斥和超时。
  - **看门狗 (Watchdog)**：Redisson 客户端提供了看门狗机制。当加锁成功后，后台会启动一个定时任务（默认锁过期时间为30s，每 10s 检查一次），只要业务逻辑还在执行，就会自动对锁进行**续期 (Renew)**，防止业务未执行完锁就过期释放的问题。
  - **脑裂问题**：在 Redis Cluster 或哨兵模式的主从切换过程中，如果主节点宕机前尚未将锁同步给从节点，新选举出的主节点可能导致多个客户端同时拿到同一把锁。可以通过 Redlock 算法缓解，但性能较差且实现复杂。
- **ZooKeeper 分布式锁**：基于 CP 模型。利用临时顺序节点实现，强一致性，不会出现脑裂导致的并发冲突，但吞吐量远不如 Redis。

## 2. JVM 与性能调优

### 2.1 OOM 排查实战套路
线上出现 `OutOfMemoryError` 时的系统性排查方法：

1. **保留现场**：JVM 启动参数必须加上 `-XX:+HeapDumpOnOutOfMemoryError` 和 `-XX:HeapDumpPath=/data/logs/`，确保在 OOM 时自动生成 Dump 内存快照。
2. **初步定位**：查看异常日志，区分是 `Java heap space` (堆内存溢出，最常见)、`Metaspace` (元空间满，多为动态代理类过多) 还是 `unable to create new native thread` (线程数超限)。
3. **工具深度分析**：将 dump 文件拉取到本地，使用 **MAT (Memory Analyzer Tool)** 打开。
4. **追溯根因**：利用 MAT 的 `Leak Suspects` 报告，查看占用内存最大的对象聚合；通过 `Dominator Tree` (支配树) 和 `Path to GC Roots` (到 GC Root 的引用链)，准确定位到是哪一行业务代码维持了对这些大对象的强引用，导致垃圾回收器无法回收。

### 2.2 Arthas 线上排障实战
Arthas 是阿里开源的 Java 诊断利器，可以做到无侵入式排查线上疑难杂症。

- **`dashboard`**：查看全局系统的实时数据看板，包含线程、内存、GC 情况。
- **`thread -n 3`**：一键打印当前最消耗 CPU 的前 3 个线程堆栈，秒级定位死循环或高并发计算瓶颈。
- **`watch`**：`watch com.example.MyService updateData "{params, returnObj, throwExp}" -n 5 -x 3`，无需重启服务，实时拦截并打印线上方法的入参、返回值和抛出的异常。
- **`trace`**：`trace com.example.MyService processRequest`，深度追踪方法调用链路的耗时，精确定位慢接口中的瓶颈方法。

## 3. 中间件与高吞吐系统 (Kafka & Redis)

### 3.1 Kafka 保障机制 (防丢失与顺序消费)
在金融级或严苛的数据流转场景中，必须保证消息的可靠性和顺序性。

- **防丢失保障**：
  - **生产端**：配置 `acks=all`，要求 Leader 写入后，必须等 **ISR (In-Sync Replicas)** 集合内所有副本同步完成，才给 Producer 返回成功。配合 Broker 端配置 `min.insync.replicas >= 2`，保证哪怕 Leader 挂了，消息也已安全落盘到其他副本。
  - **消费端**：关闭自动提交位移 (`enable.auto.commit=false`)，在业务逻辑完全成功处理完消息、落库后，再手动提交 offset，防止消费者挂掉导致消息丢失。
- **顺序消费保障**：
  - 核心原理：Kafka 只能保证**单 Partition 内的消息是有序的**。
  - 实现方案：在发送消息时，指定一个业务标识（如 `orderId`）作为 **Message Key**。Kafka 生产者会根据该 Key 的 Hash 值取模，将同一笔订单的所有状态流转消息强制发往同一个 Partition。消费端采用单线程消费该 Partition（或者使用带分发缓冲的单线程池），以此实现严格的顺序消费。

>

### 3.2 Redis 深度：高可用防御与多级缓存
Redis 在大规模高并发下，常遇到“缓存三剑客”问题，需要体系化防御。

- **缓存穿透**：查询完全不存在的数据，导致直击 DB。**防御**：采用 **布隆过滤器 (Bloom Filter)** 提前拦截。
- **缓存雪崩**：大量热点 Key 同一时间集中过期，或 Redis 集群宕机。**防御**：给过期时间加上**随机数**，打散失效时间点。
- **缓存击穿**：某一个绝对高热点的 Key 在过期瞬间，大量并发击穿打到 DB。**防御**：使用**互斥锁 (如 Redis 的 `SETNX`)**，发现缓存失效时，只有一个线程能拿到锁去查 DB 并重建缓存，其他线程自旋等待或返回默认值。

> [!IMPORTANT]
> **二级缓存机制 (L1 + L2)**：在高可用架构中，即使是 Redis 集群也可能发生网络抖动或大面积不可用。
> 引入本地缓存（如 Caffeine 或 Guava）作为 **L1 级缓存**。请求到达服务后，先查内存 Caffeine，没有再查 Redis (L2)，最后才查 DB。
> 这样即使 Redis 完全宕机，Caffeine 也能扛住绝大部分读流量，保护下游数据库存活，是极强的**防线 (护城河)**。

## 4. MySQL 索引与事务

### 4.1 B+ 树索引原理
在海量数据查询中，索引结构直接决定了系统的性能瓶颈。
- **为什么选 B+ 树**：相比于 B 树，B+ 树的非叶子节点不存储数据，只存储主键，因此单个节点能容纳更多索引，**树的高度更低**（通常 3-4 层即可支撑千万级数据），极大减少了磁盘 I/O 次数。且叶子节点用双向链表连接，天然支持**范围查询**。
- **聚簇索引 vs 非聚簇索引**：
  - InnoDB 的主键索引是**聚簇索引**，叶子节点直接存储完整的行数据。
  - 普通索引（非聚簇索引）的叶子节点只存储**主键值**。当通过普通索引查询完整数据时，需要先查到主键，再回主键索引查数据，这个过程叫**回表**。
- **覆盖索引 (Covering Index)**：如果查询的列（如 `SELECT id, name`）恰好都被包含在一个联合索引 `(name, age)` 中，就可以直接从普通索引树上拿到所需数据，**免去回表操作**，性能极佳。

### 4.2 事务与 MVCC (多版本并发控制)
- **四大隔离级别**：读未提交、读已提交 (RC)、可重复读 (RR, InnoDB 默认)、串行化。
- **幻读的解决**：在 RR 级别下，InnoDB 通过 **MVCC** 解决快照读的幻读问题，通过 **Next-Key Lock (间隙锁 + 行锁)** 解决当前读（如 `FOR UPDATE`）的幻读问题。
- **MVCC 核心机制**：
  - 依赖每行数据隐藏的两列：`DB_TRX_ID` (最后修改事务 ID) 和 `DB_ROLL_PTR` (回滚指针)。
  - 当数据被修改时，旧版本数据被放入 **Undo Log**，形成版本链。
  - 查询时生成 **ReadView (读视图)**，包含当前活跃事务列表，用来判断哪个版本的数据对自己可见。**RC 与 RR 的唯一区别在于 ReadView 生成的时机**（RC 每次 SELECT 生成新视图，RR 仅在事务第一次 SELECT 时生成）。

### 4.3 慢查询优化实战
排查线上慢 SQL 的标准三板斧：
1. **开启慢查询日志**：配置 `slow_query_log=1` 和阈值 `long_query_time=1`（秒）。
2. **`EXPLAIN` 分析执行计划**：重点看 `type` 字段（至少达到 `range` 或 `ref`，绝不能是 `ALL` 全表扫描）和 `Extra` 字段（如果出现 `Using filesort` 或 `Using temporary` 必须优化，如果出现 `Using index` 说明用到了覆盖索引，非常好）。
3. **最左前缀原则**：联合索引 `(a, b, c)`，查询时必须按顺序匹配。如果跳过 `a` 直接查 `b`，或者 `a` 用了范围查询（`>`, `<`），那么后面的字段将无法使用索引。

## 5. Spring Boot 核心原理

### 5.1 IOC 容器与依赖注入
- **IOC (控制反转)**：将对象的创建和依赖关系管理从业务代码中剥离，交由 Spring 容器统一管控，极大地降低了组件间的耦合度。
- **BeanFactory vs ApplicationContext**：
  - `BeanFactory` 是基础容器，采用懒加载（获取 Bean 时才实例化）。
  - `ApplicationContext` 是增强版容器，通常采用**预加载**（启动时实例化所有单例 Bean），并支持事件发布、国际化等企业级特性。
- **注入方式推荐**：强烈推荐**构造器注入**。相比于 `@Autowired` 字段注入，构造器注入能保证 Bean 在实例化时依赖已经就绪，并且可以将被注入字段声明为 `final`，避免被修改，也更利于写单元测试。

### 5.2 AOP 动态代理机制
- **核心概念**：AOP（面向切面编程）的核心是将那些与业务无关、却被业务模块共同调用的逻辑（如日志记录、权限校验、事务控制）封装起来。`@Transactional` 注解底层就是通过 AOP 实现的。
- **两种代理模式**：
  - **JDK 动态代理**：基于接口。通过 `Proxy.newProxyInstance` 在运行期生成接口的实现类。缺点是如果目标类没有实现接口，就无法使用。
  - **CGLIB 动态代理**：基于继承。通过修改字节码生成目标类的子类。缺点是无法代理 `final` 修饰的方法或类。
- **注意**：从 Spring Boot 2.x 开始，默认强制使用 CGLIB 代理（`spring.aop.proxy-target-class=true`），哪怕你的类实现了接口。

### 5.3 自动配置 (Auto-Configuration) 魔法
Spring Boot "开箱即用"的核心在于其强大的自动配置机制。
- **`@SpringBootApplication`** 本质上是一个复合注解，核心是 **`@EnableAutoConfiguration`**。
- **SPI 机制加载**：启动时，Spring Boot 会利用 `SpringFactoriesLoader` 去扫描所有依赖 Jar 包中的 `META-INF/spring.factories`（Spring Boot 3.x 后改为 `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`）文件，拿到所有的配置类全限定名。
- **按需装配**：拿到配置类后并不是全盘加载，而是利用大量的 **条件注解 (`@Conditional`)** 进行判断。比如 `@ConditionalOnClass(DataSource.class)` 表示只有 classpath 中引入了对应的数据源依赖，这个配置类才会生效并向容器注册 Bean。

**🧑‍💼 面试官**：你能讲讲 Spring Boot 的自动配置底层是怎么实现的吗？能举个具体的例子吗？

**🙋 您的话术**：
> "Spring Boot 能够做到开箱即用的核心在于 `@EnableAutoConfiguration` 注解。

## 6. 微服务治理与分布式架构

### 6.1 注册中心与服务发现
- **Nacos vs Eureka vs Consul**：
  - `Eureka` (Netflix)：AP 模型（高可用）。只保证可用性不保证强一致性。节点对等，挂了不影响其他节点。目前已停止维护。
  - `Consul` (HashiCorp)：CP 模型（强一致性）。基于 Raft 协议，主节点挂了在重新选举期间服务不可用。
  - `Nacos` (阿里开源)：**支持 AP 与 CP 模式切换**（通过配置临时实例或持久实例）。功能丰富，天然集成配置中心。是目前国内最主流的选型。

### 6.2 熔断与限流 (Sentinel)
在微服务中，如果下游服务（如调用大模型 API）突然变慢或超时，大量线程会阻塞等待，最终耗尽 Tomcat 线程池导致整个服务瘫痪，这就叫**雪崩效应**。
- **断路器 (Circuit Breaker) 状态机**：
  - `Closed` (关闭状态)：正常放行流量。
  - `Open` (打开状态)：当异常比例或慢调用达到阈值，断路器打开，后续请求直接 **快速失败 (Fail-fast)**，执行 Fallback 降级逻辑，保护系统。
  - `Half-Open` (半开状态)：过一段时间后，放几个试探请求过去，如果成功了就恢复为 Closed，失败了继续 Open。
- **Sentinel 的优势**：支持基于 QPS 限流、并发线程数限流、慢调用比例熔断，且自带友好的控制台，支持热更新规则。

### 6.3 分布式事务 (最终一致性方案)
- **为什么不用 2PC (两阶段提交) / XA**：强一致性方案，需要锁定资源，阻塞时间长，性能极差，高并发微服务下几乎不用。
- **Seata AT 模式**：无侵入的分布式事务方案，通过代理数据源，自动生成 `undo_log` 回滚日志来实现补偿，适合业务代码改造难度大的老系统。
- **基于 MQ 的最终一致性 (最主流方案)**：
  - 核心痛点：如何保证"本地数据库写入"和"发送消息到 MQ"这两个操作的原子性？
  - **本地消息表方案**：在本地数据库建一张独立的消息表。业务逻辑和写入消息表在一个 DB 事务中提交。然后开一个定时任务不断扫描消息表，将未发送的消息推送到 Kafka。只要 Kafka 接收成功，就更新消息表状态。
  - 此方案保证了 **At-least-once (至少一次投递)**，消费端必须结合 Redis 做**幂等性处理**，防止重复消费。

#### 🗣️ 模拟面试问答 (Q&A)

**🧑‍💼 面试官**：在你们复杂的微服务架构里，如果跨多个服务调用，你们是怎么处理分布式事务的？

**🙋 您的话术**：
> "在我们的 OTT 网关项目中，有一个核心链路：设备首次注册上线时，我们需要在核心 MySQL 里写设备建档信息，同时需要发消息通知下游的计费服务，并且还要更新 Redis 里的状态。这就是一个典型的跨数据源的分布式事务。
> 
> 我们评估过强一致性的方案（比如 Seata AT 模式），但因为设备上线会有短时并发洪峰，我们需要极高的吞吐量，不能接受长时间锁定数据库资源。所以我们果断采用了**基于本地消息表 + Kafka 的最终一致性方案**。
> 
> **具体落地是这样的**：
> 1. 我们在 MySQL 里建了一张单独的 `t_message_outbox` (本地发件箱表)。
> 2. 当设备注册请求过来时，我们开启一个普通的本地 DB 事务，把业务数据插入设备表，同时把要发给下游的 Payload 作为一条记录插入发件箱表。因为它们在同一个 DB 事务里，这就完美保证了**'业务操作'和'消息暂存'的原子性**。
> 3. 然后，后台有一个异步的轮询线程（或者用 Debezium 监听 Binlog），不断把发件箱表里的待发送消息推送到 Kafka。
> 4. Kafka 保证将消息投递给下游的计费微服务。这里我们容忍了极短时间的延迟（可能几百毫秒），换取了主业务的高可用。
> 
> **闭环兜底**：当然，这个方案是 At-least-once 的，可能会重发。所以我们在下游消费端，利用 Redis 做了基于 MessageID 的严格幂等拦截，确保即使收到重复通知，计费逻辑也绝对不会多算。"
