# JVM 与线上问题排查专项（SOP 版）

这页不是重复背 JVM 概念，而是专门训练面试中的**线上排障表达**：遇到 OOM、CPU 飙高、线程池打满、连接池耗尽、接口慢、死锁时，能说出一套可执行的 SOP。

> [!TIP]
> 回答排障题不要只说“用 Arthas 看一下”。更稳的结构是：**监控确认现象 -> 保留现场 -> 工具定位 -> 代码或配置修复 -> 复盘沉淀**。

---

## 一、线上排障总流程

### 1. 先判断影响面

- **是否单实例故障**：看同服务其他实例是否正常。如果只有一台异常，优先摘流、保留现场、再分析。
- **是否全链路故障**：看网关错误率、接口 RT、下游依赖、数据库、Redis、MQ 是否同时异常。
- **是否流量突增**：看 QPS、并发数、请求来源、热点参数，避免把容量问题误判成代码 Bug。

### 2. 保留现场再处理

- CPU 高：保留 `top -Hp`、`jstack`、Arthas `thread -n` 结果。
- 内存高/OOM：保留 GC 日志、HeapDump、`jstat` 结果。
- 线程阻塞：保留线程栈、线程池指标、连接池指标。
- 慢接口：保留链路追踪、慢 SQL、下游 RT、接口入参样本。

### 3. 快速止血优先

线上故障不要一上来就追求根因完美。常见止血动作包括：摘掉异常实例、临时限流、打开降级开关、扩容实例、暂停消费、回滚版本、隔离坏消息。

---

## 二、核心工具箱

### 1. JDK 原生命令

- **`jstat -gcutil <pid> 1000`**：每秒查看 GC 状态，重点看 YGC、FGC、Old 区使用率是否持续上涨。
- **`jmap -dump:format=b,file=heap.hprof <pid>`**：手动导出堆内存快照。生产慎用，可能造成短暂停顿。
- **`jinfo -flags <pid>`**：查看 JVM 启动参数，确认是否配置 HeapDump、GC 日志、GC 算法。
- **`jstack <pid>`**：导出线程栈，用于排查死锁、线程阻塞、CPU 飙高。
- **`top -Hp <pid>`**：查看 Java 进程内哪个线程最耗 CPU。

### 2. Arthas 高频命令

- **`dashboard`**：看线程、内存、GC、运行时信息总览。
- **`thread -n 3`**：查看当前最耗 CPU 的线程堆栈。
- **`thread -b`**：查看阻塞其他线程的线程，适合排查死锁和锁等待。
- **`trace 类名 方法名`**：看一次调用链路里每个方法耗时。
- **`watch 类名 方法名 "{params, returnObj, throwExp}" -x 3`**：观察方法入参、返回值和异常。
- **`jad 类名`**：反编译线上类，确认线上代码是否和预期版本一致。

### 3. MAT 离线分析

- **Leak Suspects**：快速看疑似泄漏点。
- **Histogram**：按类统计对象数量和浅堆大小。
- **Dominator Tree**：看谁真正保留了最多内存。
- **Path to GC Roots**：看对象为什么没被回收，是被静态变量、线程、本地缓存还是集合持有。

## 三、场景 1：OOM 深度排查

**面试官问**：线上 OOM 你怎么排查？

**回答模板**：

> “我会先保护现场，而不是马上重启。生产 JVM 参数里我们会提前配置 `-XX:+HeapDumpOnOutOfMemoryError` 和 `-XX:HeapDumpPath=/data/dump/`，保证 OOM 发生时自动留下 Dump。
> 
> 事发后先看监控，确认是堆内存、元空间，还是 native thread 不够。如果是堆 OOM，我会结合 GC 日志判断 Full GC 后老年代是否仍然降不下来。如果降不下来，说明大概率有对象被长期引用。
> 
> 拿到 Dump 后用 MAT 看 `Leak Suspects` 和 `Dominator Tree`，找到保留内存最大的对象。比如看到一个巨大的 `ArrayList` 或 `HashMap`，再通过 `Path to GC Roots` 看它是被哪个 Service、静态变量、线程上下文或者本地缓存引用住的。
> 
> 修复上，如果是一次性大查询，就改成分页、游标或流式处理；如果是缓存泄漏，就换成 Caffeine 并设置 `maximumSize` 和过期策略；如果是流量突增导致对象分配太快，就要配合限流和扩容。最后在测试环境压测验证，并把这类问题沉淀到 Code Review 规则里。”

**常见根因**：

- 一次性查询几十万行数据放入 List。
- 本地缓存没有容量上限或过期策略。
- 大文件上传、导入、导出一次性读入内存。
- 日志、报错上下文、Trace 信息拼接过大。
- 流量突增，请求对象创建速度超过 GC 回收能力。

## 四、场景 2：CPU 飙高

**面试官问**：线上 CPU 打满，你怎么定位？

**回答模板**：

> “CPU 高我会先区分是业务线程高，还是 GC 线程高。
> 
> 传统方式是先用 `top -c` 找到 Java 进程 PID，再用 `top -Hp <pid>` 找到最耗 CPU 的线程 TID，把 TID 转成 16 进制后，到 `jstack` 结果里搜索对应的 `nid`，就能看到具体堆栈。
> 
> 如果线上有 Arthas，我会直接用 `thread -n 3` 看最耗 CPU 的线程。如果堆栈停在业务代码，比如循环、正则、JSON 序列化、加解密，说明是业务逻辑或算法问题；如果是 GC Thread 占用高，就转向内存和 GC 排查，看是不是对象分配太快或老年代回收不掉。
> 
> 止血上，如果是单实例异常，先摘流；如果是流量造成的，先限流或扩容；如果是某个接口触发，会临时关闭入口或降级，再修复代码。”

**高频根因**：

- 死循环或递归没有出口。
- 正则回溯严重。
- 大 JSON 序列化/反序列化。
- 日志打印过大对象。
- 频繁 Full GC。
- 加密、压缩、图片处理等 CPU 密集逻辑没有隔离。

## 五、场景 3：线程池打满

**面试官问**：接口大量超时，发现线程池满了，你怎么处理？

**回答模板**：

> “线程池打满我会先看三个指标：活跃线程数、队列长度、拒绝次数，再结合任务执行耗时判断是流量太大，还是任务变慢。
> 
> 如果活跃线程满、队列持续上涨，说明线程池已经没有消化能力。接下来要看线程栈：如果大量线程卡在数据库、Redis、HTTP 调用上，根因可能是下游慢；如果卡在锁上，可能是锁竞争；如果都在执行业务计算，可能是 CPU 型任务过重。
> 
> 止血上，不能简单把最大线程数调很大。更安全的是入口限流、打开降级、隔离慢接口、必要时扩容实例。如果是异步任务，可以暂停消费或降低拉取速率，让系统先恢复。
> 
> 修复上要按业务类型拆线程池，核心链路和非核心链路隔离；队列必须有界；拒绝策略要明确，核心请求快速失败或降级，非核心任务进入 MQ 补偿。最后补充线程池监控和告警，避免下次满了才知道。”

**排查重点**：

- 是否使用无界队列导致内存堆积。
- 是否所有业务共用一个线程池。
- 是否把远程调用放进核心线程池。
- 是否缺少超时，导致线程长期阻塞。
- 是否下游慢调用引发级联阻塞。

## 六、场景 4：数据库连接池耗尽

**面试官问**：服务报获取数据库连接超时，你怎么排查？

**回答模板**：

> “数据库连接池耗尽一般不是简单把连接数调大就完事。我会先看 HikariCP 的活跃连接数、空闲连接数、等待连接线程数，以及数据库端当前连接数和慢 SQL。
> 
> 如果连接都被占满，要看线程栈里这些线程正在执行什么 SQL，是否有慢查询、锁等待、大事务，或者事务里夹杂了远程调用导致连接长时间不释放。
> 
> 止血上可以临时限流、杀掉异常慢 SQL、回滚问题版本，必要时扩容只读实例或服务实例。但根因修复通常是优化慢 SQL、缩短事务范围、给接口设置超时、避免在事务里调用外部服务。
> 
> 参数上连接池最大连接数要和数据库承载能力匹配，不是每个服务都配 100。微服务实例一多，总连接数可能直接把数据库打满。”

**常见根因**：

- 慢 SQL 占住连接。
- 事务范围过大，连接迟迟不释放。
- 数据库锁等待。
- 连接池配置过小或实例数扩容后总连接数失控。
- 代码泄漏连接，少见于现代框架，但老项目要警惕。

## 七、场景 5：接口突然变慢

**面试官问**：一个接口线上突然从 100ms 变成 3s，你怎么查？

**回答模板**：

> “慢接口我会先用链路追踪拆时间，而不是只看应用日志。看耗时主要花在网关、业务代码、数据库、Redis、MQ 还是第三方接口。
> 
> 如果链路追踪显示数据库慢，就看慢 SQL、执行计划、锁等待；如果 Redis 慢，就看是否有大 Key、热 Key、网络抖动；如果第三方接口慢，就看超时、重试和熔断是否生效；如果业务代码慢，可以用 Arthas `trace` 定位具体方法耗时。
> 
> 同时我会对比发布时间和流量变化：是不是刚上线引入了 N+1 查询、循环调用远程接口、日志打印过大对象，或者某个热点参数导致缓存击穿。
> 
> 止血优先级是先降级、限流或回滚，避免慢接口拖垮线程池。根因确认后再做 SQL 优化、缓存保护、异步化或批量接口改造。”

## 八、场景 6：死锁与线程假死

**面试官问**：线上程序假死，怎么判断是不是死锁？

**回答模板**：

> “死锁的典型表现是 CPU 不一定高，但请求一直卡住，线程数和等待数上升。排查时可以用 `jstack <pid>` 或 Arthas `thread -b`。
> 
> 如果是 Java 层死锁，`jstack` 通常会直接打印 `Found one Java-level deadlock`，并指出两个线程分别持有哪些锁、等待哪些锁，以及代码行号。
> 
> 修复思路是打破死锁四要素里最容易控制的部分：统一加锁顺序，减少锁粒度，不在锁内做远程调用，必要时用 `tryLock` 设置超时，拿不到锁就降级或重试。”

**补充**：不是所有“假死”都是 Java 死锁，也可能是数据库锁等待、连接池耗尽、线程池阻塞、下游接口无超时。

## 九、GC 日志快速判断

面试中不一定要逐行分析 GC 日志，但要能讲出判断方向。

- **Young GC 很频繁，但 Old 区稳定**：通常是对象创建速度快，但大多能回收。关注吞吐和停顿是否可接受。
- **Old 区持续上涨，Full GC 后降不下来**：重点怀疑内存泄漏或长期存活对象过多。
- **Full GC 频繁且停顿长**：接口 RT 会抖动甚至超时，要结合 Dump 找对象来源。
- **晋升失败或大对象直接进老年代**：关注年轻代大小、大对象分配、批量查询和大数组。
- **元空间 OOM**：关注动态代理、类加载器泄漏、频繁热部署。

常用参数表达：

- `-Xms` 和 `-Xmx` 生产建议设为一致，减少堆伸缩抖动。
- `-XX:+HeapDumpOnOutOfMemoryError` 和 `-XX:HeapDumpPath` 用于 OOM 保留现场。
- JDK 8 用 `-XX:+PrintGCDetails`、`-Xloggc`；JDK 9+ 使用 `-Xlog:gc*`。
- G1 可通过 `-XX:MaxGCPauseMillis` 设置期望停顿目标，但它不是硬保证。

## 十、总结话术

> “我处理线上问题的原则是先止血、再定位、后复盘。止血阶段保证服务可用，比如摘流、限流、降级、回滚；定位阶段用监控、链路追踪、Arthas、JDK 工具和 Dump 分析找到根因；修复阶段不仅改代码，还会补监控、告警、压测用例和 Code Review 规则，避免同类问题重复发生。”
