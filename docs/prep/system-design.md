## 1. 高可用 AI 对话网关设计

**考察场景**：如何设计一个能支撑百万用户并发对话的大模型后端网关？

**核心架构设计思路**：
1. **流式响应与降延迟 (TTFT)**：
   - 放弃传统的 HTTP 短轮询或长轮询，**全面采用 HTTP SSE (Server-Sent Events)** 协议。大模型文本生成本质是单向推送，SSE 相比 WebSocket 更轻量，能在模型吐出第一个 Token 时立刻推给前端，极限压缩首字延迟 (TTFT)。
2. **多轮对话的“无状态”转化为“有状态”**：
   - LLM 接口本身是无状态的。在网关层基于 **Redis** 构建会话上下文缓存。使用 `SessionID` 作为 Key，将用户的历史对话组装成 JSON 数组。为防止 Context Window 爆掉，引入滑动窗口机制（只保留最近 10 轮对话）或结合大模型的 Summarize 能力对历史进行压缩。
3. **隔离与熔断兜底 (Fallback)**：
   - LLM 推理属于重度长耗时 I/O 请求。为防止 Tomcat/Netty 的核心工作线程池被耗尽，必须为大模型请求分配**独立的隔离线程池**，并配置 `CallerRunsPolicy` 拒绝策略。
   - 引入降级机制：一旦主模型接口（如百度灵医/文心）超时，网关立刻重试或降级调用备用的低成本模型，或者返回缓存的预设兜底话术。

## 2. 海量时序数据存储架构

**考察场景**：面对 200 万在线 IoT 设备，每天产生数亿条心跳与遥测数据，如何设计底层存储与链路？

**核心架构设计思路**：
1. **流量削峰与异步解耦**：
   - 面对设备上线或早晚高峰的请求洪峰（如峰值 3000 QPS），在业务服务前置 **Kafka** 集群。网关仅做鉴权和极简校验，将数据丢入 Kafka 立即返回（ACK），极大地提升了系统的吞吐上限。
2. **异构双写存储设计 (MySQL + TDengine)**：
   - 绝对不要用单一的关系型数据库硬扛。
   - **MySQL (关系库)**：专门存储“稳态”数据，即设备的固件版本、拥有者、认证状态等极少变动的数据。
   - **TDengine (时序库)**：专门存储“瞬态”数据，即高频的心跳和温湿度、电压等遥测日志。利用其“一个设备一张表”的设计和列式存储的极高压缩率，不仅查询历史趋势的速度提升了数量级，磁盘占用也急剧下降。
3. **顺序消费保障**：
   - 对同一个设备的状态流转（如：上线 -> 下线）必须保证时序。在投递 Kafka 时，以 `DeviceID` 作为 Partition Key 保证同一个设备的消息打入同一分区，并在消费端自研基于 Hash 的本地单线程队列执行，杜绝并发乱序。

## 3. 分布式高并发防抖限流系统

**考察场景**：面对微服务大面积雪崩时的“告警风暴”，或弱网下设备疯狂重试导致的消息堆积，系统如何自保？

**核心架构设计思路**：
1. **基于特征值的精准拦截**：
   - 不能做全局无脑限流。提取请求的特征属性（比如：日志异常堆栈的前 500 个字符 Hash 值，或者 MQTT 的 `MessageID` + `DeviceID`）。
2. **分布式原子判重机制**：
   - 引入 **Redis + Lua 脚本** 保证多线程与分布式环境下的原子操作。
   - 对于普通的短时间防抖（如 10 分钟内不重复报警），直接使用 `SETNX` 配合 TTL（过期时间）即可，轻量且高效。
   - 对于严格频控（如 1 分钟内只能发 5 次请求），采用 **Redis ZSET 滑动窗口** 算法，记录每个特征值的时间戳，实时剔除过期窗口的记录，精准统计频率。
3. **L1 本地缓存防热点穿透**：
   - 如果瞬间洪峰过大，Redis 的网络 I/O 也会成为瓶颈。在应用侧再加一层 **Caffeine (本地缓存)** 作为 L1。当特征值被拦截后，短期内直接在 JVM 内存中被丢弃，连 Redis 都不需要查，彻底打死重复流量。
4. **死信队列 (DLQ) 处理毒药消息**：
   - 遇到极度异常且导致消费端不断抛出 Exception 的消息，如果不妥善处理会造成 Kafka 消费者一直卡在当前 Offset。引入重试计数器，超过 3 次重试失败直接将该消息塞入独立的 DLQ 队列，并移动主队列的 Offset，保证大盘业务正常运转。
