## 1. 高可用 AI 对话网关设计

**考察场景**：如何设计一个能支撑百万用户并发对话的大模型后端网关？

**核心架构设计思路**：
1. **流式响应与降延迟 (TTFT)**：
   - 放弃传统的 HTTP 短轮询或长轮询，**全面采用 HTTP SSE (Server-Sent Events)** 协议。大模型文本生成本质是单向推送，SSE 相比 WebSocket 更轻量，能在模型吐出第一个 Token 时立刻推给前端，极限压缩首字延迟 (TTFT)。
2. **多轮对话的“无状态”转化为“有状态”**：
   - LLM 接口本身是无状态的。在网关层基于 **Redis** 构建会话上下文缓存。使用 `SessionID` 作为 Key，将用户的历史对话组装成 JSON 数组。为防止 Context Window 爆掉，引入滑动窗口机制（只保留最近 10 轮对话）或结合大模型的 Summarize 能力对历史进行压缩。
3. **隔离与熔断兜底 (Fallback)**：
   - LLM 推理属于重度长耗时 I/O 请求。为防止 Tomcat/Netty 的核心工作线程池被耗尽，必须为大模型请求分配**独立的隔离线程池**，并配置 `CallerRunsPolicy` 拒绝策略。
   - 引入降级机制：一旦主模型接口（如百度灵医/文心）超时，网关立刻重试或降级调用备用的低成本模型，或者返回缓存的预设兜底话术。

#### 🗣️ 模拟面试问答 (Q&A)

**🧑‍💼 面试官**：如果 SSE 连接在弱网下断开了，客户端重连时，大模型需要从头开始重新推理吗？怎么处理断点续传？

**🙋 您的话术**：
> "不需要从头推理。这个问题**我们**在早期确实遇到过。痛点是，在弱网环境下，用户的移动端经常出现闪断，导致大模型生成了一半的回答丢失。如果让大模型重新推理，不仅浪费了昂贵的算力，用户还要重新等待 **首字延迟 (TTFT)**，体验极差。
> 
> 为了解决这个问题，**我们**设计了一套类似文件下载的『断点续传』方案。具体来说，网关层会将大模型吐出的流式响应在本地内存池或 **Redis** 中做暂存。每个增量 Token 都会被赋予一个递增的 **`Offset`**，并且整个对话请求拥有一个唯一的 **`MessageID`**。当网络断开、客户端发起重连时，会在请求头中带上 `MessageID` 和最后接收到的 **`Last_Offset`**。网关接到重连请求后，不再重新调大模型，而是直接从缓存中将 `Last_Offset` 之后已经生成但尚未发送的 Token，继续推给前端。
> 
> 这样改造后的收益非常明显，**不仅算力成本降低了 15% 左右，弱网下的重连体验也变得丝滑无感**，大模型真正做到了'续写'而非'重写'。"

> [!TIP]
> 这里的断点续传不仅展示了对 SSE 协议状态管理的深刻理解，也展现了对降低大模型算力成本 (Token 开销) 和提升用户体验 (降低重试延迟) 的双重把控。

## 2. 海量时序数据存储架构

**考察场景**：面对 200 万在线 IoT 设备，每天产生数亿条心跳与遥测数据，如何设计底层存储与链路？

**核心架构设计思路**：
1. **流量削峰与异步解耦**：
   - 面对设备上线或早晚高峰的请求洪峰（如峰值 3000 QPS），在业务服务前置 **Kafka** 集群。网关仅做鉴权和极简校验，将数据丢入 Kafka 立即返回（ACK），极大地提升了系统的吞吐上限。
2. **异构双写存储设计 (MySQL + TDengine)**：
   - 绝对不要用单一的关系型数据库硬扛。
   - **MySQL (关系库)**：专门存储“稳态”数据，即设备的固件版本、拥有者、认证状态等极少变动的数据。
   - **TDengine (时序库)**：专门存储“瞬态”数据，即高频的心跳和温湿度、电压等遥测日志。利用其“一个设备一张表”的设计和列式存储的极高压缩率，不仅查询历史趋势的速度提升了数量级，磁盘占用也急剧下降。
3. **顺序消费保障**：
   - 对同一个设备的状态流转（如：上线 -> 下线）必须保证时序。在投递 Kafka 时，以 `DeviceID` 作为 Partition Key 保证同一个设备的消息打入同一分区，并在消费端自研基于 Hash 的本地单线程队列执行，杜绝并发乱序。

#### 🗣️ 模拟面试问答 (Q&A)

**🧑‍💼 面试官**：Kafka 如果发生 Rebalance 导致消息重复消费，你们怎么保证业务幂等性？

**🙋 您的话术**：
> "这是个经典痛点，Kafka 的 **Rebalance** 经常会导致同一批消息被不同消费者重复拉取，如果不做控制，下游业务就会出现数据多算或覆盖错误。**我们**的方案是多维度保障的。
>
> 考虑到不同业务场景，**我们**做了两层防线。第一层拦截在缓存侧：针对不可变的操作（例如触发告警），**我们**利用设备日志自带的时序递增 **`MessageID`**。消费端在真正处理业务前，会拿 `DeviceID_MessageID` 作为 Key，向 **Redis** 发起一次 **`SETNX`** 操作，设置一个较短的过期时间（例如 10 分钟）。如果返回 0，说明近期已经处理过了，直接丢弃这条重复消息。
> 
> 第二层是利用时序数据库的天然防重特性。对于高频上报的遥测数据，这些日志里都会带有精确到毫秒的时间戳。在写入 **TDengine** 时，我们把 `(DeviceID, Timestamp)` 作为主键。这样即使发生了重复消费，TDengine 的底层设计是针对同一时间戳的数据执行 **覆盖写 (Upsert)** 操作。这样不用写额外的防重逻辑，就能天然实现幂等。
> 
> 这套组合拳的收益在于，对于高频数据**我们**依赖底层组件的天然特性以达到极致性能，对于低频告警**我们**通过缓存拦截，在完全不影响 Kafka 吞吐量的前提下，做到了 100% 的业务数据准确性。"

> [!TIP]
> 提到利用 TDengine 的“同一时间戳覆盖写”不仅自然地实现了幂等，还能够体现出你对异构存储特性的灵活运用。

## 3. 分布式高并发防抖限流系统

**考察场景**：面对微服务大面积雪崩时的“告警风暴”，或弱网下设备疯狂重试导致的消息堆积，系统如何自保？

**核心架构设计思路**：
1. **基于特征值的精准拦截**：
   - 不能做全局无脑限流。提取请求的特征属性（比如：日志异常堆栈的前 500 个字符 Hash 值，或者 MQTT 的 `MessageID` + `DeviceID`）。
2. **分布式原子判重机制**：
   - 引入 **Redis + Lua 脚本** 保证多线程与分布式环境下的原子操作。
   - 对于普通的短时间防抖（如 10 分钟内不重复报警），直接使用 `SETNX` 配合 TTL（过期时间）即可，轻量且高效。
   - 对于严格频控（如 1 分钟内只能发 5 次请求），采用 **Redis ZSET 滑动窗口** 算法，记录每个特征值的时间戳，实时剔除过期窗口的记录，精准统计频率。
3. **L1 本地缓存防热点穿透**：
   - 如果瞬间洪峰过大，Redis 的网络 I/O 也会成为瓶颈。在应用侧再加一层 **Caffeine (本地缓存)** 作为 L1。当特征值被拦截后，短期内直接在 JVM 内存中被丢弃，连 Redis 都不需要查，彻底打死重复流量。
4. **死信队列 (DLQ) 处理毒药消息**：
   - 遇到极度异常且导致消费端不断抛出 Exception 的消息，如果不妥善处理会造成 Kafka 消费者一直卡在当前 Offset。引入重试计数器，超过 3 次重试失败直接将该消息塞入独立的 DLQ 队列，并移动主队列的 Offset，保证大盘业务正常运转。

#### 🗣️ 模拟面试问答 (Q&A)

**🧑‍💼 面试官**：你能手写或者解释一下 Redis ZSET 滑动窗口限流的 Lua 脚本核心伪代码吗？

**🙋 您的话术**：
> "没问题。**我们**之所以用 **Lua 脚本**配合 Redis，主要是为了解决高并发场景下的竞态问题，确保限流逻辑是原子的。痛点在于，如果不用 Lua，应用端执行 `获取 - 判断 - 写入` 的过程中，网络延迟和并发会导致判断失效。
>
> 核心思路是用 **ZSET (有序集合)** 来模拟滑动窗口，其中 `Score` 是请求的时间戳，`Value` 是保证唯一性的请求 ID。脚本逻辑大概分四步：
> 1. 首先，**我们**要清理掉滑动窗口之外的过期数据。通过 `redis.call('ZREMRANGEBYSCORE', key, 0, current_time - window_size)` 剔除掉陈旧记录。
> 2. 然后，统计当前窗口内剩余的有效请求数，即 `local count = redis.call('ZCARD', key)`。
> 3. 接着进行判断：如果 `count < limit`，说明没超过阈值。**我们**就用 `redis.call('ZADD', key, current_time, unique_id)` 把当前请求加进去，并顺手给整个 Key 续期 `EXPIRE` 防止内存泄漏，最后返回 1 表示放行。
> 4. 如果超出了 `limit`，那就直接返回 0，也就是拦截该请求。
>
> 采用这段脚本后，**我们**成功把微服务雪崩时的几十万告警风暴拦截在了网关层外，Redis 服务器单节点的 QPS 被压榨到了几万依然稳定，成功保护了后端的数据库资源。"

> [!TIP]
> 解释代码时，思路一定要清晰：先清理、再统计、后判断、最后更新状态。顺手提到 `EXPIRE` 防内存泄露是非常加分的工程细节。
