# Gemini 模拟面试复盘 - AI Agent 架构与底层技术

- **面试轮次**: 模拟面试
- **日期**: 2026-06-17
- **岗位**: AI Agent 架构师 / 研发工程师

## 面试问题记录

### 1. ReAct 范式与执行流
- **【提问】**：在 Agent 的核心范式与推理编排中，ReAct (Reasoning and Acting) 是目前最经典且应用最广泛的模式之一。请你从底层逻辑的角度详细讲讲：ReAct 范式的标准工作流是怎样的？它相比于仅让大模型使用 CoT (Chain of Thought) 进行推理，本质上解决了什么核心痛点？
- **【你的回答】**：reaact 主要是思考、行动、结果，模型先思考要解决什么问题，调用哪个工具，然后获取工具的结果，然后在继续循环直到拿到结果为止，COT 是思维链，让 llm 一步一步的去执行，在遇到复杂问题时，会进入死循环。本质上解决了 oct 的进入死循环问题。
- **【面试官点评】**：你的回答抓住了 ReAct 的核心执行流。不过，纯 CoT 的核心痛点其实不是“死循环”，而是**缺乏外部反馈导致的事实幻觉（Hallucination）和知识盲区**。ReAct 引入外部工具的 Observation，本质上是为了给推理提供实时的事实锚点（Grounding）。恰恰相反，在工程部署中，带有工具调用的 ReAct 往往比纯 CoT 更容易陷入“死循环”。
- **【💡 核心要点总结】**：ReAct 工作流为“思考 (Thought) -> 行动 (Action) -> 观察 (Observation)”。它相比纯 CoT 的核心优势在于**引入了外部反馈机制**，提供了实时事实锚点，从而有效缓解了大模型依靠静态参数推理所带来的事实幻觉。在工程落地时需通过架构设计防范工具调用失败引发的死循环。

### 2. Function Calling 与自我纠错
- **【提问】**：大语言模型是如何“理解”你传入的工具列表并准确触发某个特定工具调用的？如果在交互闭环中，工具返回了参数解析失败或执行超时等异常情况，你会如何设计反馈机制来引导模型自我纠错（Self-Correction）并从异常中恢复？
- **【你的回答】**：获取@tool 注解的类，方法，提取方法名，入参和描述组成 json 放到提示词中。如果出现参数解析失败和超时等异常，首先加上重试机制，如还未解决，就需要反馈给人工干预。
- **【面试官点评】**：对底层 Schema 转换理解清晰。但在异常恢复上，实现“Self-Correction”的核心技巧是：**将异常本身（如 JSON 解析报错）作为一种“观察结果（Observation）”返回给大模型**。大模型看到错误后，会在下一轮思考中主动修正参数并重新发起调用，这才是 Agent 具有自主性（Autonomy）的体现。
- **【💡 核心要点总结】**：大模型理解工具的底层逻辑是框架通过反射提取代码注解（类、方法名、入参、描述），将其转换为 **JSON Schema** 注入 Prompt 中。真正的“自我纠错（Self-Correction）”并非依靠简单的工程代码重试，而是**将异常报错明细作为 Observation 传回给 LLM**，利用其上下文理解能力自主调整参数并重试发起调用。

### 3. 长短期记忆与上下文管理
- **【提问】**：随着 Agent 执行的任务越来越复杂，你是如何界定和设计 Agent 的短期记忆（Context）与长期记忆的？当上下文逼近 Token 上限时，有哪些主流的策略来压缩记忆？向量数据库在这个过程中如何发挥作用？
- **【你的回答】**：短期记忆主要是最近几轮对话，放 redis，超过上限用模型压缩；长期记忆主要是用户画像，存向量数据库，提示词中先用 rag 搜索。节省 token 策略：1. 小模型压缩；2. 集成 llmlingua 算法，计算每个 token 的容忍度，删除容忍度低的。
- **【面试官点评】**：回答非常专业，特别是提到了前沿的 **LLMLingua 算法**进行无损 Token 裁剪。补充细节：1. 长期记忆不仅是用户画像，还包含历史成功经验（Few-shot）和 SOP。2. 检索时机通常不是盲目全盘检索，而是由 Agent 根据 Thought 触发 SearchMemory 工具按需检索。
- **【💡 核心要点总结】**：短期记忆（最近对话）常存于 Redis，超限时利用小模型摘要或使用 **LLMLingua 算法（基于 Token 信息熵）**进行无损裁剪。长期记忆包含用户画像、成功经验 (Few-shot) 和标准作业程序 (SOP)，存入向量数据库。长期记忆不应每次全量载入，而应交由 Agent 主动调用 `SearchMemory` 工具**按需检索**以避免撑爆上下文。

### 4. Agent 框架抽象 (LangChain vs LangGraph)
- **【提问】**：为什么在构建复杂生产级 Agent 时，传统的 LangChain 会显得非常吃力，而 LangGraph 能更好地解决这个问题？它们底层的状态管理机制有什么本质区别？
- **【你的回答】**：langchain 主要是 COT，状态流转只存在于单个 agent。langGraph 主要有 stage、node、edge、条件 edge。stage 是状态，node 是 agent，edge 是流转条件。
- **【面试官点评】**：总结非常精准。传统 LangChain 的 Chain 抽象本质上是线性的 DAG（有向无环图），很难处理反复横跳的逻辑。LangGraph 通过引入**状态机（State Machine）模型**，不仅支持多 Agent 共享状态，更重要的是打破了 DAG 限制，允许**循环（Cycles）**的存在，完美支持“执行-反思-重试”逻辑。
- **【💡 核心要点总结】**：传统 LangChain 基于有向无环图 (DAG) 或线性流程，难以处理复杂的循环和跳转。LangGraph 采用**状态机（State Machine）抽象**，将上下文定义为全局 State，Agent/工具作为 Node 修改状态，流转依赖 Edge 与 Conditional Edge。这种架构允许**循环 (Cycles)** 的存在并支持多 Agent 状态共享，是实现复杂 Agent 编排的底层基石。

### 5. Multi-Agent 协同与防死循环
- **【提问】**：业界常见的 Multi-Agent 组织架构主要有哪些模式？在多 Agent 交互中，如果陷入“死循环辩论”，你会引入什么样的机制来打破僵局强制收敛？
- **【你的回答】**：主子架构，主 agent 做任务拆分并分发，一般决策由主 agent 决定，重要部分推送人工干预。
- **【面试官点评】**：点出了最常用的 Hierarchical（层级/Supervisor）模式和 Human-in-the-loop。但针对“收敛”问题，系统架构中还需引入硬性机制：1. **Max Steps（最大轮次限制）**：达到阈值必须进入降级分支。2. **裁判机制（Evaluator/Judge Agent）**：引入判别能力极强的第三方 Agent，满足条件时强制输出 FINISH 指令结束流转。
- **【💡 核心要点总结】**：多智能体主流组织架构为 **Hierarchical（层级/Supervisor模式）**。为打破交互中陷入的信息茧房或死循环辩论，必须在架构底层引入硬性收敛机制：一是设置全局最大执行轮次限制（**Max Steps / Iteration Limit**）进行熔断；二是引入高判别能力的**裁判机制（Evaluator/Judge Agent）**，一旦判定目标完成即强行输出指令终止流转。

### 6. 系统自动化评估 (Evaluation)
- **【提问】**：面对高度非确定性的输出，你会如何设计一套自动化的评估流水线（Eval Pipeline）？会重点关注哪些指标及采取什么技术手段评估幻觉率与工具调用准确性？
- **【你的回答】**：记录下每次工作的内容流转、输出结果等，按照固定的评估规则让专门的 agent 去评估。
- **【面试官点评】**：直接点出了核心的 **全链路追踪（Tracing）** 与 **LLM-as-a-Judge**。在量化落地中，幻觉率评估需比对外部真实信息（Context）计算 Groundedness（忠实度）得分；工具调用准确性除了依赖主观打分，还会结合传统的确定性断言（如 Exact Match 完全匹配参数）。
- **【💡 核心要点总结】**：自动化评估流水线（Eval Pipeline）的核心基建是**全链路追踪（Tracing）结合 LLM-as-a-Judge**。评估幻觉率（Groundedness）主要依靠对比外部真实 Context 与最终输出计算忠实度；评估工具调用准确率则结合确定性断言（Exact Match），直接比对 Trace 记录中的 JSON 参数与预期结果。

## 总结与改进方案

- **优势**: 拥有极强的工程落地直觉，对大模型底层机制（反射 Schema、LLMLingua、状态机编排）理解透彻。
- **不足**: 部分系统设计的应对策略略偏向传统微服务（如简单的异常重试机制），而在发挥 Agent 原生自主思考能力（如基于报错提示自我纠错 Self-Correction）的应用上可进一步深化。
- **Next Step**: 重点复习分布式系统/Agent设计上的硬性兜底机制，将 LangGraph 的 Supervisor 模式和 Evaluator Agent 裁判机制在接下来的业务代码中尝试落地。
